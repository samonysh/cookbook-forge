# 组织层写作规范：让一章有弧、有链、有张力

> 适用对象：`cookbook-forge` 阶段 2 的章节提纲、阶段 3 的逐章 MDX 写作、阶段 6 的 `chapter-lint` 复核。
> 解决的核心病症：**段落本身都通顺，但整章读下来像一份分类目录——每节自成一块，节与节之间没有承接，机制全堆在前面，章尾突然结束，读者的问题链在第三段就断了。**
> 与 `references/readability-style-guide.md` 的分工：那份管句子与段落（R1–R12 / W1–W6），本份管段落以上（章、节、论证链、术语主线）。两份不重复；冲突判定见第 4 节。

---

## 0. 一句话原则

**每一章都是一个问题的完整回答：章首把问题立起来，主体一节接一节地把它拆小、答掉、留下新的小问题，章末回到最初那个问题，说明读者的认识被改成了什么样。**

Schimel 把这条原则表述为「作者的工作是让读者的工作变简单」（*Writing Science* 第 1 章）；Booth 等人把它表述为「引言是语境—问题—回应的三段式」（*The Craft of Research* 第 14 章）。两者说的是同一件事：读者不是来收集信息的，是来追一个问题的答案的。问题链一断，后面写得再好也读不下去。

这条原则在三个尺度上同时成立（Schimel 第 10 章的「嵌套弧」）：

- **章**：O（读者处境）→ C（本章问题）→ A（各节回答）→ R（认识变化）。
- **节**：开头承接上一节留下的问题，结尾交出一个更小的问题或宣布关闭。
- **段**：首句承接已知，末句承载新信息（这一层已由 R4/R6/R9 管，本规范不重复）。

---

## 1. 规则清单

编号 `O1–O9`。标「机检」的条目由 `scripts/chapter-lint.mjs` 的 `G1–G6` 自动判定；标「人工」的进第 7 节自查清单。

### O1 章弧闭合：章首立问题，章末回到同一个问题

- **规则**：`N.0` 必须给出一个**可回答的问题**（不是主题名）。主体各节都在回答它的某个子问题。章末最后两个正文节里，必须出现一次「回到章首问题」的回收，并说明认识发生了什么变化：原来以为 X，现在知道是 Y。
- **判定**：三条同时满足才算合格。
  1. `N.0` 内有问句，或有「本章要解决的问题是 / 本章回答」这类显式问题句。
  2. 章末两节的正文里复现了章首问题中的核心词（至少 2 个实词）。
  3. 章末有一句认识变化句（`原来/此前以为 / 现在知道 / 不再是…而是… / 真正决定…的是`）。
- **依据**：Schimel 的 OCAR 四要素与「故事是螺旋而非圆圈」（第 4 章：结尾必须回到开头，但开头已经位移）；Booth 等的「引言三件套 + 结论回应问题」（第 14 章）；*Docs for Developers* 每章以 Corg.ly 的具体场景开场、章末回到同一场景收束。
- **反例**（真实样书第 3 章，脱敏引用）：
  > `## 3.9 双线索引与下一章`
  > \- **应用线**：3.1 最小示例与完整任务 → 3.2 四步落地、模式矩阵、参数与边界 → 3.3 症状表、冒烟脚本、排错顺序。
  > \- **原理线**：3.4 Schema 编译 → 3.5 因果链与不变量 → …
  > 下一章讲工具。**工具模式的输出本身就是一个隐式工具**……
  这条结尾只做了目录复述和下一章预告，没有回答 3.0 提出的「怎样让模型稳定返回可校验对象，第一次不合法时系统知道怎么办」。读者读完知道「这章讲了什么」，但不知道「最初那个问题现在怎么答」。
- **改后**：
  > 回到 3.0 的问题：模型第一次返回不合法时，系统靠什么知道该怎么办？现在可以给出完整回答——靠三件东西同时到位：输出先被编译成可校验的 Schema（3.4），失败被转成一条可回喂的消息而不是异常（3.4.3），重试有明确的预算归属和终点（3.6）。最初以为「写对 `output_type` 就够了」，现在知道它只决定请求载荷的形状，不决定失败之后怎么走。
- **机检**：`G1`（章首问题句）+ `G2`（章末核心词回收）；第 3 条认识变化句为人工。

### O2 问题链：每节承接上一节留下的问题

- **规则**：每个 H2（`N.0`/`N.10` 除外）的第一段，在前两句内完成一次交接，三选一：
  - **回指结论**：「上一节说明了……」
  - **点出缺口**：「但这只解释了请求形状，没解释失败之后走哪条路。」
  - **复用术语**：直接以上一节结尾留下的名词作主语（「这条重试路径有两个分叉点」）。
  同时，节末最后一句要移交：给出下一节要回答的问题，或明确宣布本问题已关闭（「到这里，X 已经能解释完」）。
- **判定**：首段没有回指、且没有复用上一节标题中的任何 2 字以上术语 → 断链。
- **依据**：Booth 等的「读者问题链」（第 5 章把论证拆成读者会追问的五问：你凭什么、这怎么推得出来）；Schimel 第 10 章的「每个小节是一条完整弧，结尾是力量位置」；中文指南 5.2「相邻段落之间能看出递进、解释、对比或因果关系」。
- **反例**（真实样书第 3 章，3.4 之后）：
  > `## 3.5 因果链：为什么必须是这个结构`
  > 把这条链拆成五环，每一环都回答「不做会怎样」：
  3.4 刚讲完「编译顺序解释了两条应用侧规则」，3.5 直接另起一张清单，读者不知道这两节是什么关系（是补充？是反驳？还是同一件事的细看？）。
- **改后**：
  > `## 3.5 因果链：为什么必须是这个结构`
  > 3.4 说明了输出要先被编译成 Schema 子类，但只回答了「请求里带什么」，没回答「为什么必须是这条链」。把这条链拆成五环，每一环都回答「不做会怎样」——五环里只要缺一环，上一节的两条规则就会失效。
- **机检**：人工。回指句的写法太多，机检误报高；`G2` 只覆盖章级回收。

### O3 漏斗：现象先于机制，机制前必须有触发场景

- **规则**：章内第一个非 `meta` 节必须是 `app`（具体任务或症状）。原理线不得连续出现 3 个以上 H2 而不插入 `app`/`synthesis`。每个原理节的首段要回指一个应用节里出现过的具体现象（报错、异常输出、成本数字、失败截图），不能凭空开始讲结构。
- **判定**：三条独立判定：首个正文节轨道；连续原理节计数；原理节首段是否含现象引用（`报错/超时/失败/异常/看到/现象/第 N 节`）。
- **依据**：Schimel 第 6 章的「漏斗」——从大问题逐步收窄，每一步只补一个未知，且每步都在回答「为了让上一步成立，我们还需要知道什么」；同章批评「先卖方案、后定义问题」的 bizzwidget 写法；*Docs for Developers* 的每一章都是先给一个具体翻车场景，再给方法。
- **反例**（把真实样书第 3 章改成「机制先行」的版本，用于对照）：
  > `## 3.1 六种 Schema 实现与七个模式字面量`
  > 框架内部并不是「一个 `output_type` 对应一个分支」，而是先把输出规格编译成 `OutputSchema` 的子类……
  这是真实存在的 3.4.1 开头。它本身写得不错，但如果把它挪到 3.1（读者还没见过任何失败），读者就不知道这六种实现是干什么用的——这正是用户指出的「开头直接抛概念」在章级的放大版。
- **改后**（保持 3.4 位置不变，只补一句现象回指）：
  > `## 3.4 原理线：一次输出在框架里经历什么`
  > 3.3 里那张症状表有三行都指向同一个疑问：为什么同一个 `output_type`，在 A 提供方走工具调用，在 B 提供方却报「不支持原生结构化输出」？答案不在 `output_type` 本身，而在它被编译成了什么。
- **机检**：`G3`（首个正文节轨道 + 连续原理节 ≥3）。

### O4 单节单弧：一节只回答一个问题

- **规则**：一个 H2 只承担一个可陈述的问题。H3 数量建议 ≤6；若超过，或节内出现两个互不依赖的问题（例如「参数怎么选」与「边界在哪」），必须拆节，或在中间插入一个综合小段把两个问题接起来。每个 H3 标题都应能改写成本节问题的子问句。
- **判定**：H3 计数 ≥8 触发提示（`G5`，提示而非限制：只提醒复核，不强制拆节）；6–7 个人工复核；每个 H3 标题读一遍，若说不出它回答的是哪个子问题，即不合格。
- **依据**：Schimel 第 10 章「每个小节应打包一个完整想法，形成自己的小弧」；Booth 等第 10 章「为论文的每个主要部分建一张 storyboard 卡，卡顶写这一节支持的判断」；Mayer 的 segmenting 原则（分段降低外在负荷）。
- **反例**（真实样书第 3 章 3.2，六个 H3）：
  > 3.2.1 四步落地 / 3.2.2 模式选择矩阵 / 3.2.3 三种模式并排跑一遍 / 3.2.4 跨字段规则 / 3.2.5 参数怎么选 / 3.2.6 边界清单
  这一节实际回答了四个不同问题：怎么做、怎么选、怎么补 Schema 管不到的规则、什么情况下不该用。读者读到 3.2.5 时已经忘了 3.2.1 的上下文。
- **改后**：拆成 `3.2 怎么落地（四步 + 并排跑一遍）` 与 `3.3 怎么选、怎么补、什么时候别用（矩阵 + 跨字段 + 参数 + 边界）`，两节各用一句问题开头，后一节首句回指前一节的结论。
- **机检**：`G5`（H3 ≥8 报警）；6–7 个与「是否两个问题」为人工。

### O5 论证五件套：判断 → 理由 → 证据 → 限定 → 回应

- **规则**：每个论证型小节（`principle`/`synthesis`）至少要能指出五样东西：
  1. **判断**：一句可被反驳的话（不是「本节介绍 X」）。
  2. **理由**：为什么这个判断成立。
  3. **证据**：代码、图、表、实测输出、源码摘录，至少一个。
  4. **限定**：在什么条件下不成立（`只适用于 / 前提是 / 超过 N 就退化 / 不能保证`）。
  5. **回应**：对最可能的反例或反直觉现象给一句解释。
  缺 3 或 4，视为「纯说理」。
- **判定**：小节内找不到任何证据锚（围栏代码、图位、表格、`source:` 标记、实测输出）且属于 `principle` → 不合格；全章所有 `principle` 节都没有证据锚 → 章级不合格。限定句与回应句为人工。
- **依据**：Booth 等第 5–8 章（claim / reason / evidence / warrant / acknowledgment and response 五要素；warrant 是「理由凭什么能推出判断」的一般原则）；中文指南 5.2 的逻辑跳跃例（「Agent 可以调用工具 → 工具用 JSON Schema → 因此要考虑重试」缺的正是 warrant）。
- **反例**（真实样书第 3 章 3.5）：
  > 把这条链拆成五环，每一环都回答「不做会怎样」：1. 业务系统需要确定性字段 → 所以输出必须被 Schema 描述……
  五环推理本身成立，但整节没有代码、图、表或实测输出，读者只能选择相信。属于「有理由、无证据」。
- **改后**：在五环之后补一张两列表（每环 → 对应的可观测证据，例如「第 2 环 → 3.4.2 的 `build()` 分派顺序」「第 4 环 → 3.3.2 冒烟脚本第二个断言失败时的消息序列」），把推理锚到已经给过的证据上。
- **机检**：`G4`（全章 `principle` 节 0 证据锚）。

### O6 术语主线：一章 3–5 个关键术语，一种叫法，章末回收

- **规则**：`N.0` 点名的核心概念不超过 5 个；同一概念全章只用一种叫法（不要「输出契约 / 输出规格 / 输出模式 / Schema」交替使用指同一层东西）；章末至少复现一次，让读者把术语和最初的问题对上。
- **判定**：`N.0` 内加粗术语 >5 个 → 过载；同一段内出现 2 个以上近义术语指同一对象 → 命名漂移；章末两节未复现任何 `N.0` 术语 → 未回收。
- **依据**：Booth 等 10.2.2「选 4–5 个贯穿全文的关键术语，并保持一致，重复比读者以为的更必要」；Schimel 的 schema 原则（新概念必须挂到读者已有的概念上，术语是挂钩）；*Docs for Developers* 的「诅咒知识」——作者内部的多个叫法会原样漏进正文。
- **反例**（真实样书第 3 章 3.0）：
  > 两者之间缺的不是「让模型更聪明」，而是一条**可校验、可失败、可重试**的通道。
  > 本章要解决的问题是：怎样让模型稳定返回可校验的 Python 对象……
  后文交替使用「输出契约」「输出 Schema」「模式」「通道」。四者其实分属三层（契约 = 业务类型；Schema = 编译产物；模式 = 请求载荷形态），但没有一处把三层并排说清，读者容易把它们当同义词。
- **改后**：在 3.0 末尾加一句分层：
  > 后文会反复出现三个词，先分清：**输出契约**指你写的业务类型；**输出 Schema** 指框架把它编译出来的内部对象；**输出模式**指这次请求把 Schema 放在工具定义、原生响应还是提示词里。三者是「你写的 → 框架编译的 → 这次请求用的」。
- **机检**：`G2` 覆盖「章末回收」；过载与命名漂移为人工。

### O7 标题即论断：H2 标题要能看出本节在论证什么

- **规则**：H2 标题三选一：问题式（「为什么必须是图而不是循环」）、判断式（「预算归属决定重试成本」）、动作链式（「从业务类型到请求载荷」）。纯名词标签（「参数」「边界」「原理」）不合格，除非它是全书统一的固定槽位（如 `N.10 本章参考`）。
- **判定**：H2 标题去掉章号后，若只剩顿号分隔的名词短语（≥2 个名词、无动词、无疑问词、无「从…到…」）→ 不合格。
- **依据**：Schimel 第 10 章「小标题用来标识本节要解决的问题」；Booth 等 10.2.3「每节卡顶写这一节支持的判断」；中文指南 5.2「每个章节有明确的问题或任务」。
- **反例**（真实样书第 3 章）：
  > `## 3.2 操作步骤、参数选择与边界`
  三个名词并列，读者看不出这一节在论证什么，也看不出和 3.1 的关系。
- **改后**：
  > `## 3.2 四步落地：先跑通，再并排对比三种模式`
  > `## 3.3 选型与边界：什么时候不该用默认模式`
- **机检**：人工。启发式提示：H2 标题含 ≥2 个顿号、无动词性词尾（`怎么/为什么/决定/必须/不能/从…到`）→ 复核。

### O8 节奏：机制段之间插场景，别让读者连读三节结构

- **规则**：连续 2 个 `principle` H2 之后必须有一个 `app` 或 `synthesis` 节。单个原理节内，连续 3 段纯机制后必须给一个具体输入/输出或失败样例。章末两节不得再开新的机制话题。
- **判定**：H2 层由轨道顺序判定；段层人工。
- **依据**：Schimel 第 3 章「concrete」与第 4 章「读者的耐心决定结构」（读得越久越需要具体物）；Merrill 的 demonstration 原则；中文指南 5.2「抽象概念有恰当的例子支撑」。
- **反例**：真实样书第 6 章的原理线有 4 个连续 `principle` 节（6.4–6.7），中间没有应用节。虽然每节内部有代码，但章级节奏上读者要连读四节结构。
  这是可辩护的设计（原理线本来就该成组），因此本规则把它列为「提示」而非「错误」，见 3.5 的 4.4。
- **改后**：在 6.6 与 6.7 之间插一个半页的「回到 6.3 的那次异常运行」小段，用已给过的失败序列复述一遍节点归属，再进入 6.7 的并行工具深潜。
- **机检**：`G3`（连续 ≥3 个原理节）。

### O9 章末不新增概念（硬规则）

- **规则**：最后两个正文节不得首次引入术语（加粗概念、新缩写、新标签）。需要预告下一章时，只允许一句回指式的前向引用：预告里的概念必须是本章已定义、已给过例子的；只写「本章哪个概念会在下一章变成主线索」，不写下一章的技术细节。
- **级别**：**硬规则，不是默认写法**。回指式钩子是唯一允许的形式；在章末新开概念即违规，无论该概念是否「只是为了预告」。
- **判定**：章末两节内首次出现的加粗术语数 >2 → 不合格；出现新缩写且未解释 → 不合格；出现新标签（含换一种说法的旧概念）→ 不合格。
- **依据**：Schimel 第 4 章「resolution 的作用是关闭，不是再开一个开头」；Booth 等第 14 章「结论要重申判断与其意义，不引入新论证」。
- **反例**（真实样书第 3 章 3.9 末句）：
  > **工具模式的输出本身就是一个隐式工具**，业务工具与输出工具共享 Schema 生成、参数校验和失败回喂；理解这一点，第 4 章会顺很多。
  它在章末引入「隐式工具」，但没有定义、没有例子。按硬规则，这不再是「可接受的钩子」，而是违规。
- **改后**（钩子降级为回指）：
  > 下一章讲工具。本章讲过的「输出也要走工具调用」在那里会变成主线索：输出工具和业务工具共用同一套 Schema 生成与失败回喂。
  这样只用本章已有的「输出工具 / Schema / 失败回喂」三个词，不引入「隐式工具」这个新标签。
- **机检**：暂无机检（需要按节统计首次出现的加粗术语，可后续扩展为 `G6`）。

## 2. 章级骨架怎么搭

### 2.1 四种结构，先选一种

Schimel 第 4 章按「读者耐心」给了四种结构，本规范默认用第一种（与现有 `N.0–N.10` 骨架一致）：

| 结构 | 顺序 | 适合 | 在本项目中的对应 |
|---|---|---|---|
| **OCAR** | 开场 → 挑战 → 行动 → 结论 | 有耐心、要看证据的读者（技术书主体章节） | 现有骨架，默认 |
| **ABDCE** | 行动 → 背景 → 发展 → 高潮 → 结尾 | 提案、要给评审快速抓住价值的章 | 可用于全书第 1 章 |
| **LDR** | 导语 → 展开 → 结论 | 杂志型长文、综述章 | 允许的变体，见 2.1.1 |
| **LD** | 导语即全部结论 → 展开 | 查阅型参考章 | 允许的变体，见 2.1.1 |

**选择规则**：默认 OCAR。只有当一章的主要用途是「查参数 / 查结论」而不是「跟着想一遍」时，才可切换为 LD/LDR（或其他读者耐心适配的变体）。

### 2.1.1 结构变体的不变量（不得动摇）

查阅型章节换结构，只换**叙述顺序**，不换**度量口径**。以下四项在任何变体下照旧成立：

1. **`track` 注解照常打**：每个 H2 上一行仍写 `<!-- track: app|principle|synthesis|meta -->`。LD 的「导语即结论」段若在 `N.0` 内，按 `meta` 计；若单独成节并给出结论，按它实际承担的轨道计，不得因为「这一段只是导语」而漏标或标成 `meta` 躲统计。
2. **双线比例仍按 `body3` 口径统计**：`ratio-count.mjs` 的统计范围与分母不变（`body3`：正文三个轨道，排除 `meta`、表格 ×0.5、代码块等既有规则）。换结构不改变任何一章参与统计的方式。
3. **综合段仍守 10%–15%**：`synthesis` 的占比下限与上限不变；**含章末回收段的章节上限放宽到 18%**，因为回收段本身计入综合层（见 9.8）。LD 把结论前置到导语，不等于把综合段挪走——综合段仍要回答「现象 ↔ 机制 ↔ 所以 ↔ 不这样会怎样」。
4. **`G1`/`G2` 仍适用**：查阅型章也要有一句可回答的问题（G1），章末也要回到它（G2）。若某变体确实无法同时满足，用 `<!-- lint-ignore: Gx -->` 注明结构原因，并在交付说明里报出。

**异常如实报，不凑数**：若某章换结构后 `body3` 比例或综合段占比超出既有区间，在阶段 6 报告里写明章号、实际比例、偏差原因，**不得为了凑回区间而挪动内容或改 `track` 标注**。结构变体是叙述许可，不是度量豁免。

### 2.2 章首（`N.0`）的四件事

在 `readability-style-guide.md` 的「困境 → 代价 → 交付 → 概念」四句骨架之上，章级还要多做三件事：

1. **给问题，不给主题**。写「怎样让模型稳定返回可校验对象，第一次不合法时系统知道怎么办」，不要写「本章介绍类型化输出」。前者可回答，后者只能被复述。
2. **划前置边界**。列出读者必须具备的 2–4 条前置知识，并说明本章**不**解决什么（Booth 的「限定研究范围」，*Docs for Developers* 的受众前置知识）。
3. **给阅读路线**。应用线 / 原理线 / 综合段各读哪几节、跳过什么会缺什么。现有模板的「本章地图」已覆盖，保持。

### 2.3 章节之间的漏斗

整本书也要有一条漏斗：上一章的结论必须成为下一章的问题来源。判定方法很简单——把每章 `N.0` 的第一段抽出来连读，如果读起来是一串并列的主题（「本章介绍 A」「本章介绍 B」），说明书级问题链断了；如果读起来是「A 已经能解释 X，但解释不了 Y，所以本章要解决 Y」，说明链在。

Schimel 第 6 章的检验法可以直接借用：**每一节只允许补一个未知**。如果一节里同时出现两个「我们还不知道……」，拆开。

### 2.4 章末（`N.8–N.9`）的三件事

1. **回收**：用 `N.0` 的原话复述问题，再给答案（不是复述目录）。
2. **认识变化**：明确写出「原来以为 X，现在知道 Y」。这一句是整章张力的释放点，缺了它，读者会觉得读了一堆零件。
3. **移交**：下一章的问题必须从本章的边界里长出来（「本章只处理了单次运行；多次运行之间怎么共享状态，是第 N+1 章的事」），而不是另起一个话题。

**硬规则（不是默认）：章末钩子只能回指，不能新开概念。** 最后两个正文节（通常是 `N.8–N.9`）允许写一句下一章预告，但必须满足：

- 预告里出现的每个概念，本章都已经定义并给过例子；
- 不得在章末首次引入加粗术语、新缩写或新标签（包括「隐式工具」这类看起来只是换个说法的标签）；
- 预告只写「本章哪个概念会在下一章变成主线索」，不写下一章的技术细节。

违反这条的钩子一律降级为回指式，或整句删除。判定与反例见 `O9`，模板 `N.9` 已按此约束固定写法。

## 4. 机检项与阈值（`chapter-lint.mjs` 的 G1–G6）

| 代码 | 检查 | 判定阈值 | 级别 | 豁免 |
|---|---|---|---|---|
| `G1` | 章首无问题句 | `N.0` 全节（去掉标题行，含 callout/引用）无 `？`，且无「本章 + 回答/解决/问题/怎么/什么/如何/为什么/目标/任务/决策」 | WARN | `<!-- lint-ignore: G1 -->` |
| `G2` | 章末未回收章首问题 | 章末两节内**找不到结构合格的回收段**：①独立成段（空行分隔，非列表/表格/标题/引用/callout/代码）；②位于双线索引与 `N.10` 之前；③同段内同时含问题复述线索（`回到 N.0` / `回到第 N 章` / `第 N.0 的问题` / `章首（开头）的问题`）与认识变化线索（`原来以为` / `此前以为` / `最初以为` / `现在知道` / `现在可以给出（完整）回答` / `不再是…而是`）。另：回收段与 `N.0` 问题句的共享实词 <2 也报。 | WARN | `<!-- lint-ignore: G2 -->` |
| `G3` | 机制先行 / 机制连堆 | 首个正文节是 `principle`；或连续 ≥5 个 `principle` H2（现有骨架允许原理线成组 3–4 节） | WARN | `<!-- lint-ignore: G3 -->` |
| `G4` | 原理线无证据锚 | 全章 `principle` 节内 0 个代码围栏 / 图位 / 表格 / `source:` 标记 | WARN | `<!-- lint-ignore: G4 -->` |
| `G5` | 单节过平（提示项） | 单个 H2 下 H3 ≥8 | WARN（提示而非限制） | `<!-- lint-ignore: G5 -->` |
| `G6` | 原理节首段缺交接 | `principle` H2 首段以反引号标识符开头，且前 120 字内无节号/「上一节」类回指、也无动机线索 | WARN | `<!-- lint-ignore: G6 -->` |

补充约定：

- 只检查 H2 层（`G5` 例外，数 H3；`G6` 例外，查 H2 首段）；`N.0`、`N.10` 与 `meta` 轨不参与 `G3`/`G4`。
- `G2` 的共享实词按「2 字滑窗 + 停用词表」计算，命中 2 个即算「词对上了」；但词对上了仍需结构合格的回收段，否则视为「只复述目录、没回答问题」。两个条件任一不满足即报。`N.0` 没有问题时（已被 `G1` 报）跳过 `G2`。
- `G2` 的结构判定只认「同一段里两类线索同时出现」。尾节正文里出现一次「回到某个实现细节」、或「下一章回到工程化」，都不再被当成收束；索引列表、表格、callout、代码块里的文字不参与。豁免条件只有两个：`<!-- lint-ignore: G2 -->`（需在交付说明里写结构原因），以及 `N.0` 无问题句（此时 `G1` 已报，`G2` 跳过）。
- `G3` 的「首个正文节」指第一个非 `meta`、非 `N.10` 的 H2；模板默认是 `app`，所以正常书稿不会误报。
- `G4` 是章级判定，只报一次，不按节刷屏；`principle` 节 <2 个的短章跳过。
- `G` 系列全部为 WARN，不因 `--strict` 升级；`--no-organization` 可整体关闭。
- `G5` 是**提示而非限制**：阈值固定为 8，不收紧到 7。它只提醒「这一节可能装了两个问题」，作者确认单弧成立后可保留，不强制拆节。
- `<!-- lint-ignore: Gx -->` 写在 H2 上方或 `N.0` 内，仅豁免该章。

## 5. 与可读性规范的分工

| 尺度 | 管什么 | 文档 | 代码 |
|---|---|---|---|
| 句子 | 长句、名词化、指代、语序 | `readability-style-guide.md` R5/R6/R9/R12 | W4/W5/W6 |

写作顺序：先按本文搭章弧与节链，再按 `readability-style-guide.md` 修句段，最后跑两套 lint。

## 9. 实测校准（一本库框架类样书，14 章）

以下数据来自一本已完稿的库框架类技术书（14 章、正文 `body3` 约 8.1 万字）。改写只动衔接、动机、句段与章末回收，不新增技术内容、不改技术判断、未移动 `track` 标注与图表位置。所有数字均可在该项目上复现，本章只保留结论，不保留书名、库名与路径。

### 9.1 主要修改动作是 O2：约 90 处节间交接

- 14 章合计补写约 90 处 H2 首段的交接或动机句，平均每章 6–9 处；其余修改（长句拆分、名词化、主题句）每章 3–5 处。
- 改写后 `W2`（概念先行）与 `G6`（原理节缺交接）均为 0 命中；`W7`（重复句）也为 0，说明插入交接句时只要顺手合并原开场句，就不会留下重复。
- **结论**：O2 是投入产出比最高的一条。它不需要重写技术段落，只在大节入口加一句「上一节给出了什么、还缺什么」，就能把分类目录改回问题链。

### 9.2 G2 的真实表现：3 章没有回收段，旧实现全部漏报

| 现象 | 实测 |
|---|---|
| 有「回到 `N.0`」回收段 | 11 章；回收段 127–257 字，多数在 180 字左右 |
| 无回收段，直接以双线索引 / 默认配置 / 下一章预告收尾 | 3 章（第 8、10、13 章） |
| 旧 `G2`（裸词表）是否报出这 3 章 | **没有** |

**为什么漏报**：旧实现用一张收束词表扫章末两节全文，表里有裸词「回到」。尾节正文里任何一次「回到某个实现细节」，或「下一章回到工程化」，都会让判定认为「已有收束句」。3 章里 1 章是下一章预告里出现「回到」，2 章是尾节正文出现「回到」。

**修复：从词表改为结构判定。** 回收段必须同时满足三条——①独立成段（空行分隔，非列表/表格/标题/引用/callout/代码）；②位于双线索引与 `N.10` 之前；③同段内同时出现「问题复述」与「认识变化」两类线索。单个词不再算数。

**反向验证（必做）**：把补写前的 3 章复制到临时书目录，用新版 `G2` 跑全书——准确报出第 8、10、13 章，其余 11 章不误报；同一轮还有 1 条 `G5`（既有基线）。这证明修复抓到的是「缺回收段」本身，不是换了一种误报。

**补写结果**：3 章各补一段（185 / 171 / 160 字，合计 516 字），都从该章「常见误区」里翻出真实误解作为 X，Y 指到具体小节。补写后全书回到 `ERROR 0 / WARN 1`（仅 `G5`），`--strict` 退出 0。三章综合段占比：9.5% → 12.4%、10.7% → 13.2%、10.0% → 12.2%，全部回到 10%–15% 区间；全书 `body3` 81944 字，综合段 11062 字，占 13.5%。

**这说明什么**：3 章内容都完整，缺的是「认识变化」这一步；`G2` 想抓的问题真实存在，只是词表太宽。属于「真问题 + 查不出」，修判定比补内容更优先——补内容只解决这 3 章，修判定解决后续所有书稿。残留的越界仅剩 2 章（16.8% / 15.8%），是个例，交项目方决定是否放宽或单列。

### 9.3 G5：一次命中，人工确认可接受

全书仅 1 次命中（某章一个 H2 下有 8 个 H3）。人工复核：8 个子节同属一条接入流程，单弧成立，保留不拆。**阈值维持 8，定位维持「提示而非限制」**；这说明 G5 的合理形态是一次命中、人工裁决，而不是清零。

### 9.4 G1 / G3 / G4 零命中说明模板比 lint 更早生效

- `G1` 全过：模板 `N.0` 的问句槽位已经把「可回答的问题」前置，作者按槽位写就不会漏。
- `G3` 全过：双线骨架本身保证首个正文节是应用线，原理线成组也不超过 4 节。
- `G4` 全过：原理节普遍带代码、表或 `source:` 摘录。

三条规则对「按模板写」的书稿近乎恒真，价值在于回归防护——防的是后续改动把首节改成原理线、把证据锚删掉。不建议因为零命中而删除。

### 9.5 回收与索引是两件事

11 章有回收段，其中多数章的 `N.9` 同时承担「回收 + 双线索引 + 下一章预告」三件事。回收段写得再好，后面紧跟两行索引，读者的结束感仍会被拉回目录。

**可固化写法**（已进模板）：`N.9` 内先独立成段写回收（首句「回到 `N.0`」，三句：问题复述 → 答案 → 认识变化），空一行，再写双线索引与回指式预告。不要把这四项压进同一段。

### 9.6 比例副作用：交接句按 1:1 计入应用/原理线

新增交接句大多落在 `app` 或 `principle` 节，会稀释 `synthesis` 占比。实测 14 章里 2 章高于 15%（16.8% / 15.8%），两章都是改写前就存在；另有 1 章因缺回收段一度低到 9.5%，补写回收段后回到 12.4%。**不为凑比例删内容，也不把交接句标成 `meta`**；上限判定见 9.8。

### 9.7 不能固化的部分

需要理解内容才能判断的三件事仍靠人工：H2 标题是否真的是论断、术语是否发生命名漂移、章末预告里的概念是否本章已定义。可固化的只有三种交接句式（缺口式 / 换轴式 / 回指式，见 `readability-style-guide.md` 8.7）与回收段四句骨架。把这三件事写成自动规则，误报率会高于收益。

### 9.8 综合段上限：含回收段章节按 18% 判定

**决策**：2 章综合段为 16.8% / 15.8%，书稿不动。章末回收段属于综合层，写完整回收（问题复述 + 答案 + 认识变化）必然抬高综合段占比，这是结构性副作用，不是内容失衡。

**规则**：

- 含章末回收段的章节，综合段上限放宽到 **18%**；下限 10% 不变。
- 未检出回收段的章节，仍按 10%–15% 判定。
- `ratio-count.mjs` 用 `--synth-max-closure`（默认 18）控制上限，报告里写明「含回收段章节按 18% 判定」，并列出哪些章适用。
- **禁止为压回 15% 而删减回收段内容，或把机制解释挪出综合段。** 回收段写短了，读者拿不到认识变化，损失大于 1–2 个百分点的比例偏差。

**实测**：全书 14 章均检出回收段（含补写的 3 章），因此全部按 18% 判定；16.8% 与 15.8% 两章不再报越界，其余章判定不变，`ratio-count` 0 条比例告警。18% 不是新目标，只是给回收段留出的空间；接近 18% 时仍应先检查是否在复述前文。
