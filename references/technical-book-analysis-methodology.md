# 技术书分析方法论：定 · 拆 · 图 · 深 · 织

> 适用对象：`cookbook-forge` 生成 CookBook / Handbook / Survey 的**前置分析阶段**。
> 目标：把「拿到一堆资料就开始套 15 章模板」改成「先判定技术对象、再拆解、再建全局地图、再逐模块递进、最后双线编排成书」。
> 本文只定义方法与落点，不替代 `SKILL.md` 的流水线；两者的关系见第 8 章。

---

## 0. 先看结论：这套方法论解决什么

现有流程的能力在「采集、排版、多格式转换、工程质检」，短板在**内容结构**。具体是四个缺口：

| 缺口 | 现状（`SKILL.md` 阶段 2–3） | 后果 |
|---|---|---|
| 拆解 | 阶段 2 给了一份固定的 15 章骨架（全景、基础、快速开始、架构、模块、Recipes……），不区分对象是领域概念、库、语言还是平台 | 写 PyTorch 和写「垃圾回收机制」用同一副骨架；章节像文档目录，不像知识结构 |
| 全局视角 | 只有「一张总览架构图 + 章节依赖表」，没有模块依赖、反馈回路、主干叙事线 | 每章单独看都成立，合起来不知道谁影响谁；读者「见树不见林」 |
| 概念→原理递进 | 章模板写的是「原理部分 → 实用部分」，概念层被压缩成一段定义，且没有递归与停止条件 | 概念解释像词典；原理讲到「是什么」就停，讲不到「为什么必须这样」 |
| 双线并行 | 同一小节里原理和用法混排，没有对位关系、没有交叉引用、没有单线可读性保障 | 想动手的读者被原理挡住，想理解的读者被代码打断；两条线都不完整 |

本文用五个动作补齐：**定（对象判定）→ 拆（多切面拆解）→ 图（全局地图）→ 深（概念→原理递归）→ 织（双线编排）**。每个动作都给出输入、产出物、完成判据（Definition of Done，下文简称 DoD），以及一个可复制的模板。

### 0.1 一页总览

```text
A0 定 ──> A1 拆 ──> A2 图 ──> A3 深 ──> A4 织 ──> 成书
│          │          │          │          │
│          │          │          │          └─ 章内双线：应用 → 原理 → 综合
│          │          │          └─ 概念锚定 → 原理链 → 递归 → 证据
│          │          └─ 五视图 + 主干叙事线 + 关系边
│          └─ 12 通用切面 + F13，选 1 主 + 2~3 辅 + 1 验证；MECE 五测
└─ 四类对象 + 混合对象规则 + 三圈边界
```

一句话记忆：**先定它是什么，再决定怎么切；切完先画关系，再往下钻；钻的时候概念在前、原理在后；成书时应用与原理两条线各自能读通。**

度量与证据层（轨道标记、`ratio-count`、验证等级 L1–L3、`metadata/verify/`）不改变这五步的结论，只负责让「比例合适」「示例可跑」这两句话可验收。

### 0.2 与「写作风格指南」的分工

- 本文管**想什么、按什么顺序想、想到什么程度算够**。
- `references/style-guide-oreilly.md` 与 `style-guide-springer.md` 管**写出来是什么语气、什么版式节奏**。
- 两者是「结构」与「文风」的关系，不互相替代。先有结构，再套文风；不要用文风掩盖结构缺失。

## 1. 现状诊断：四个缺口分别在哪儿发生

### 1.1 拆解缺口：一套骨架套所有对象

`SKILL.md` 阶段 2 的典型结构是「全景 → 基础概念 → 快速开始 → 安装 → 核心概念 → 架构 → 关键模块 → 调用链 → 配置扩展 → Recipes → 性能安全 → 测试调试 → 部署 → 生态 → 总结」。这套骨架对**平台/框架**基本成立，但：

- 对「迁移学习」这类**领域概念**：没有「安装」「部署」「测试调试」，却必须有「方法族谱、假设条件、负迁移、评测协议、开集边界」。
- 对「Python 语言」这类**语言**：核心不是「安装 + API」，而是「语义模型、对象模型、协议、运行时、并发与内存」。
- 对「Agent 设计」这类**设计问题**：核心是「决策循环、工具契约、上下文管理、失败恢复、评测」，而不是「模块清单」。

**根因**：把「书的目录」当成了「技术的结构」。目录应该由结构推导出来，而不是先有目录再往里填。

### 1.2 全局缺口：只有全景图，没有关系网

现有 `ch00-overview` 要求「一张总览图 + 阅读路线 + 章节依赖表」。问题是：

- 图里通常只有「包含/分层」，没有**依赖方向、数据流、反馈回路、替代关系**。
- 「章节依赖表」是阅读顺序依赖，不是**技术因果依赖**。
- 正文跨章引用是「见第 3 章」的跳转，缺少「因为第 3 章的 X 约束，第 7 章才必须用 Y」的因果交代。

**判据缺失**：没有一条规则能回答「这张地图画到什么程度算够」。

### 1.3 递进缺口：概念层塌陷成定义，原理层停在现象

章模板的「原理部分」实际上承担了三件事：概念解释、机制说明、设计权衡。三件事挤在一段里，结果是：

- 概念用「XX 是一种……」的词典句式，读者能复述但不能判断。
- 原理只讲「它做了什么」，不讲「不做会怎样」「为什么只能是这个顺序」。
- 没有递归：遇到「调度器」「依赖注入」这类本身还能拆的机制，要么一句带过，要么无限展开。

**根因**：缺少分层标准（概念层/原理层/分解层/证据层）和**停止条件**。

### 1.4 双线缺口：混排不等于并行

现有模板是「原理 → 实用 → 表格 → 图 → 解释」的线性节奏。它看似兼顾，实际是**单线穿插**：

- 应用线的任务被原理段落切碎，读者无法「只读应用线完成任务」。
- 原理线依赖前文代码，抽掉代码后论证断裂。
- 没有比例控制：概念书可能 80% 在讲 API，工具书可能 80% 在讲源码。

**根因**：没有把「应用」和「原理」当成两个**可独立成立的视角**来设计，只当成两种段落类型。

### 1.5 一句话诊断

> 现有流程擅长「把资料变成合规的书」，不擅长「把技术变成有结构的 knowledge」。本文补的是后者。

## 2. A0 定：先判定对象类型，再决定怎么拆

### 2.1 为什么要先定类型

同一句「讲清楚 React」，三种理解会产出三本完全不同的书：

- 把它当**库**：讲 API、组件、Hooks、生态、最佳实践。
- 把它当**机制**：讲虚拟 DOM、协调算法、Fiber、调度、并发渲染。
- 把它当**语言/范式**：讲声明式 UI、单向数据流、组件组合模型。

类型判定错，后面所有切面、章节、双线比例都会错。**类型不是标签，是拆解策略的选择器。**

### 2.2 四类对象与混合对象

| 类型 | 代号 | 典型对象 | 读者真正想要的 | 默认叙事主干 |
|---|---|---|---|---|
| 领域概念 / 机制 | **T1** | 迁移学习、垃圾回收、Agent 设计、CAP、事务隔离 | 建立心智模型，能判断适用边界 | 问题 → 机制 → 权衡 → 边界 |
| 库 / 框架及生态 | **T2** | PyTorch、FastAPI、React、Dapr | 能上手、能选型、能排错、能扩展 | 任务 → 能力 → 机制 → 生态 |
| 编程语言 / 语言应用 | **T3** | Python、JavaScript、SQL、Python 数据分析 | 掌握语义与运行时，写出符合语言习惯的代码 | 语义 → 运行时 → 惯用法 → 工程 |
| 系统 / 平台 / 协议 | **T4** | Kubernetes、PostgreSQL、HTTP/3、消息队列 | 理解全局结构与运行路径，能运维与扩展 | 上下文 → 容器 → 组件 → 运行 → 运维 |

**混合对象规则**（很常见，必须显式处理）：

1. 以「读者要完成的任务」定**主类型**，另一类型作为**深潜模块**，不平均用力。
2. 例：「PyTorch 自动微分」= T2 外壳（怎么用 `autograd`）+ T1 内核（计算图与反向传播）。主类型 T2，第 4–5 章切到 T1 深潜。
3. 例：「Python 的 GIL」= T3 语言运行时 + T1 并发机制。主类型 T3，GIL 单独成章按 T1 写。
4. 混合对象在 `00-object.md` 中必须写一句：**「本书 70% 按 T2 组织，第 4、5 章按 T1 深潜，原因是……」。

### 2.3 判定流程（5 问，按顺序问）

```text
Q1 读者会不会「调用它」？            会 → 进入 Q2；不会 → T1
Q2 它有没有「安装/部署/运维」面？      有 → T4；没有 → 进入 Q3
Q3 它是不是「写代码所用的语言本身」？  是 → T3；不是 → T2
Q4 它的核心价值是「提供能力」还是「解释现象」？ 能力 → T2；解释 → T1
Q5 它的边界是否由「协议/接口标准」定义？ 是 → T4；否 → 按 Q1–Q4 的多数证据定
```

判定时不要只看对象名词，要看**读者动作**：

- 读者动作是「调用 / 配置 / 集成」→ T2 或 T4。
- 读者动作是「理解 / 判断 / 设计」→ T1。
- 读者动作是「用这门语言表达」→ T3。

### 2.4 类型 → 拆解策略（核心选择表）

| 维度 | T1 领域概念 | T2 库/框架 | T3 语言 | T4 系统/平台 |
|---|---|---|---|---|
| 主切面 | F13 概念/机制（T1 专用） | F07 能力矩阵 + F01 层次/栈 | F13 概念/语义 + F04 生命周期 | F01 层次/栈（上下文→容器→组件） |
| 辅助切面 | 演进史、失败模式、使用场景 | 调用链、生态、演进史、失败模式 | 范式、生态、演进史、失败模式 | 运行时/数据流、质量属性、失败模式、演进史 |
| 验证切面 | 能力矩阵（能否覆盖读者任务） | 使用场景（任务能否落到章节） | 能力矩阵 | 使用场景 |
| 默认双线比例（应用:原理，不含综合段） | 45:55 | 55:45 | 50:50 | 60:40 |
| 章内双线重心（顺序固定：应用→原理→综合） | 应用做验证，原理承载主叙事 | 应用先行，原理按需深潜 | 写法与语义/运行时等重 | 部署运维先行，原理解释约束 |
| 章节粒度重心 | L2 机制 | L2 模块 + L3 机制 | L3 语义/运行时机制 | L2 容器 + L3 组件 |
| 最容易写错的地方 | 写成百科词条 | 写成 API 文档 | 写成语法教程 | 写成部署手册 |

> 比例不是硬指标，是**默认值**。目标值写在 `04-dual-track.md` 的章级对位表（「目标比例」列），**不要写进章节 frontmatter**；成稿后由 `scripts/ratio-count.mjs` 按轨道标记实测，脚本负责回填 frontmatter 的 `ratio` 并与目标比对（6.6）。

### 2.5 边界：三圈法

类型决定「怎么切」，边界决定「切到哪儿停」。

| 圈层 | 定义 | 写法 | 不该出现的內容 |
|---|---|---|---|
| 核心圈 | 本书必须讲透、能独立成章的对象 | 概念→原理→递归→证据，完整展开 | 无 |
| 协作圈 | 与核心圈有接口、但不由本书负责的对象 | 只讲「接口契约 + 何时需要 + 去哪查」 | 内部实现细节 |
| 环境圈 | 背景、历史、竞品、生态 | 一段话或一张表，给定位 | 独立章节（除非读者明确要求） |

**边界测试**：对每个候选模块问一句「如果删掉它，读者还能完成本书承诺的 3 件事吗？」

- 能，且它属于协作圈/环境圈 → 降级为段落或附录。
- 不能 → 进核心圈。

### 2.6 读者能力与成功标准

拆解前必须写清三件事，否则「做够了」没有判据：

1. **起点能力**：读者已经会什么（具体到「能写 Python 函数」而不是「有基础」）。
2. **终点能力**：读完能**独立完成**什么（可观测动作：实现、选型、排错、评审）。
3. **不承诺**：本书不讲什么（防止范围蔓延）。

终点能力用**可观测动词**写，避免「理解」「掌握」这类不可验证词。可借用 Bloom 修订版认知层级（记忆→理解→应用→分析→评价→创造）作为动词库；本书默认要求至少到「应用」，核心章到「分析/评价」。

### 2.7 A0 的输入、产出与 DoD

| 项 | 内容 |
|---|---|
| 输入 | 用户需求、资料清单、目标读者描述、输出格式 |
| 产出 | `metadata/analysis/00-object.md`（对象判定 + 边界 + 读者 + 成功标准） |
| DoD-1 | 主类型已判定，混合对象已写明主/辅类型与理由 |
| DoD-2 | 核心圈模块数量在 6–15 之间（少于 6 说明没拆开，多于 15 说明粒度太细或边界失控） |
| DoD-3 | 终点能力 3–7 条，全部是可观测动作 |
| DoD-4 | 「不承诺」至少 3 条，且与用户确认过 |
| DoD-5 | 每条判定都有资料或用户陈述作为证据，不靠猜 |

### 2.8 `00-object.md` 模板

```markdown

## 一句话定义
<对象> 是 <类别>，它让 <读者> 能够 <完成什么>，代价是 <主要约束>。

## 类型判定
- 主类型：T2 库/框架（证据：读者要调用 API、有生态与版本、需要安装）
- 辅类型：T1 机制（第 6 章深潜调度器）
- 判定路径：Q1 会调用 → Q2 无部署面 → Q3 非语言 → Q4 提供能力 → T2

## 边界
### 核心圈（必须讲透）

### 协作圈（只讲接口）

### 环境圈（只给定位）

- 起点：能 ...
- 终点：能独立 ...

2. 读完能 ...
```

## 3. A1 拆：多切面拆解与「不重不漏」验证

### 3.1 拆解不是分目录

「拆解」要回答的是：**这项技术由哪些子问题/子模块构成，它们各自解决什么、边界在哪、为什么这些而不是那些。**

分目录只是拆解的结果之一。如果先想目录再填内容，会得到「看起来整齐但彼此不可比」的章节——有的章讲一个 API，有的章讲一个时代。

### 3.2 十二个通用切面 + 一个 T1 专用切面

切面（facet）是观察同一对象的**一种一致视角**。一次只用一个切面切，才能保证切出来的模块在同一抽象层上。

F01–F12 是通用切面；F13 只在对象为「领域概念/机制」（T1）或需要深潜机制时使用，它也是 T1 的主切面。

| 编号 | 切面 | 它问的问题 | 切出来的模块长什么样 | 最适合 |
|---|---|---|---|---|
| F01 | 层次 / 栈 | 从使用者到最底层，中间经过哪些层？ | 接口层、编排层、执行层、存储层、内核层 | T2/T4/T3 |
| F02 | 组成 / 构件 | 系统由哪些部件组成，各自职责与接口？ | 路由、校验、依赖注入、序列化 | T2/T4 |
| F03 | 数据 / 状态 | 有哪些核心数据、状态机与存储？ | 请求上下文、会话、缓存、索引、事务状态 | T4/T2/T1 |
| F04 | 生命周期 | 一个对象/请求/任务从生到死经历什么阶段？ | 创建、初始化、运行、暂停、销毁；编译、加载、执行 | T3/T4/T2 |
| F05 | 控制流 / 调用链 | 一次操作按什么顺序经过谁？ | 入口、中间件链、调度、回调、异常传播 | T2/T4 |
| F06 | 数据流 | 数据从哪里来、被怎样变换、到哪里去？ | 采集、清洗、特征、推理、落库、回流 | T1/T2 |
| F07 | 能力矩阵 | 它能做哪些事，不能做哪些事？ | 训练、推理、分布式、部署、可观测 | T2/T1 |
| F08 | 使用场景 / 任务 | 谁在什么情境下用它完成什么？ | 上手、单机、生产、多租户、迁移 | T2/T4 |
| F09 | 质量属性 | 性能、安全、可靠、成本、可维护性如何取舍？ | 延迟预算、隔离级别、限流、降级、审计 | T4/T1/T3 |
| F10 | 演进史 | 它为什么变成现在这样，哪些设计是历史包袱？ | 版本代际、范式迁移、兼容层、废弃路径 | T1/T3/T2 |
| F11 | 生态 / 关系 | 上下游、插件、竞品、标准如何影响它？ | 包管理、扩展点、协议、替代方案 | T2/T4 |
| F12 | 失败模式 | 它会在哪里坏、怎么坏、如何诊断？ | 错误分类、反模式、边界条件、排障路径 | 全部 |
| F13 | 概念 / 机制（T1 专用） | 它由哪些核心概念与机制构成，概念之间是什么关系？ | 问题定义、核心机制、方法族、边界条件 | T1；T2/T3 的深潜章 |

> 两个**横切产出**不单独算切面，但每个切面都要留下痕迹：
> - **概念卡**：切出来的每个模块，记录它引入的核心概念（供 A3 概念层使用）。
> - **决策记录（DDR）**：每个「为什么这样设计」记一条决策、备选方案与代价（供原理层使用）。

### 3.3 切面怎么选：1 + 2~3 + 1

不要把所有切面都用一遍。规则：

1. **主切面 1 个（或同族的 1 组）**：由对象类型决定（见 2.4）。主切面应产出 60%–80% 的模块。
2. **辅助切面 2–3 个**：用来补主切面漏掉的维度，并制造交叉验证。
3. **验证切面 1 个**：不产新模块，只检查「读者任务能否落到某个模块」。默认用 F08（T1/T3/T4）或 F07（T2）。

选择辅助切面的三个启发：

- 主切面偏**静态**（F01/F02）→ 辅一个**动态**（F04/F05/F06）。
- 主切面偏**能力**（F07）→ 辅一个**边界**（F09/F12）。
- 主切面偏**当下**（F01–F09）→ 辅一个**时间**（F10）或**关系**（F11）。

**反例**：同时用 F01、F02、F05 三个结构/行为切面切同一层，切出来的模块会大量重叠（路由层既是「层」又是「构件」又是「调用链节点」），MECE 必然失败。切面之间要**互补**，不要**同义**。

### 3.4 粒度：五级与三条硬规则

| 层级 | 名称 | 规模 | 在书里的位置 |
|---|---|---|---|
| L0 | 领域 | 1 个 | 书名 / 全书主题 |
| L1 | 子系统 / 部分 | 3–6 个 | Part（部/篇） |
| L2 | 模块 | 6–15 个 | 章（每章一个读者问题） |
| L3 | 机制 | 每章 2–5 个 | 节（每条因果链） |
| L4 | 实现 | 按需 | 代码块 / 源码解析 / 附录 |

三条硬规则：

1. **一章 = 一个 L2 模块 = 一个读者问题**。一个模块如果要回答两个不相关的问题，拆；如果两个模块回答同一个问题，并。章长不设固定预算，按模块权重分配（见 6.6）。
2. **一节 = 一个 L3 机制 = 一条完整因果链 = 800–2000 字**。讲不完说明该机制应升为 L2 独立成章；讲不到 800 字说明它只是细节，降为段落。
3. **L4 只在「关键路径」或「证据需要」时展开**，单节占比不超过 50%。源码是证据，不是正文。

**粒度均匀性**：同一父节点下，最大模块与最小模块的预估字数比应 ≤ 3（与模块权重 3:1 对齐）。超出时先怀疑拆法，而不是硬凑字数。

### 3.5 拆解五步

```text
S1 立主干问题：一句话写出「本书要帮读者解决的那个总问题」。
S2 主切一刀：用主切面切出 5–9 个候选模块，允许粗糙。
S3 辅助补漏：每个辅助切面问一次「主切面漏了什么」，只增补，不重切。
S4 合并/拆分：按 3.4 的三条规则整理，命名统一为「动词 + 对象」或「名词 + 职责」。
S5 MECE 验证：跑 3.6 的五个测试，不通过就回到 S2/S4。
```

**命名规则**（直接影响可读性）：

- 模块名用「职责」而不是「技术名词」。`认证与授权` 优于 `JWT`；`请求生命周期` 优于 `Middleware`。
- 同一层用同一词性。不要混用「路由」「做校验」「Redis」。
- 模块名里不出现「高级」「进阶」「其他」——这三个词是拆解失败的信号。

### 3.6 MECE 五测

| 测试 | 做法 | 不通过的表现 | 修法 |
|---|---|---|---|
| T1 排他测 | 任取两个模块，各用一句话说「它负责什么、不负责什么」 | 两句话有重叠 | 合并，或把重叠部分抽成第三模块 |
| T2 穷尽测 | 把资料主题清单与读者任务清单逐条映射到模块 | 有主题/任务无处安放 | 补模块，或明确降级到协作圈/环境圈 |
| T3 反向测 | 每个模块反向找证据：至少 1 条资料或 1 个读者任务 | 模块找不到来源 | 删除（臆造）或补资料 |
| T4 层级测 | 同一父节点下的子模块是否同一抽象层 | 「路由」和「用 Redis 做限流」并列 | 上移/下移其中一个 |

## 4. A2 图：全局分析，既见树木又见森林

### 4.1 全局分析要回答的三个问题

拆解得到的是「零件清单」，全局分析要回答：

1. **合起来产生了什么？** 单个模块都不具备、只有组合后才出现的行为（整体性/涌现）。
2. **变化如何传播？** 改一个模块，哪些模块会受影响；哪些影响是单向的，哪些会回来（反馈）。
3. **读者该按什么顺序理解？** 一条能解释「为什么这一章必须排在这一章之后」的主干叙事线。

只画一张「包含关系」架构图，回答不了这三个问题。

### 4.2 五视图

五个视图不是五张装饰图，每个视图对应一类**必须被写进正文的断言**。

| 视图 | 回答的问题 | 必须出现的元素 | 对应正文落点 |
|---|---|---|---|
| **V1 上下文/边界** | 它和外部世界交换什么？ | 外部参与者、输入、输出、不变量、明确不负责的部分 | ch00 + 每章「位置声明」 |
| **V2 结构/依赖** | 谁依赖谁、谁调用谁、谁是枢纽？ | 模块节点、依赖方向、同步/异步、强弱依赖、分层 | ch00 总图 + 各章接口段 |
| **V3 运行时/数据流** | 一次真实操作经过哪些模块？ | 3–5 条关键场景（正常、峰值、失败）、时序、数据形态变化 | 生命周期/调用链章 |
| **V4 反馈回路** | 哪些影响会回来？哪些会自我强化或自我修正？ | 增强回路（R）、调节回路（B）、延迟、触发条件 | 性能/稳定性/生态章 |
| **V5 演进** | 现在的结构里哪些是历史选择？ | 时间线、拐点、被保留的兼容层、已废弃路径 | 演进章/章末注记 |

#### 为什么必须有 V4（反馈回路）

大多数技术书只画 DAG（有向无环图），但真实系统里最危险、最有解释力的部分恰恰是回路。例：

- **缓存**：命中率↑ → 延迟↓ → 流量↑ → 热点集中 → 击穿 → 延迟↑（增强转调节，带延迟）。
- **重试**：失败↑ → 重试↑ → 下游负载↑ → 失败↑（正反馈，雪崩）。
- **生态**：用户↑ → 插件↑ → 能力↑ → 用户↑（增强回路）；同时维护负担↑ → 质量↓（调节回路）。

回路不需要精确建模，但必须写出：**回路方向、延迟位置、什么条件下失控**。这三件事直接决定「陷阱」章节的质量。

### 4.3 关系边的写法

模块之间不能只画一条线，每条边要能读成一句因果话。

| 边类型 | 连接词 | 例子 |
|---|---|---|
| 依赖 | 「没有它，X 无法启动/编译/成立」 | 校验依赖 schema 定义 |
| 调用 | 「X 在 … 时调用 Y」 | 路由在匹配后调用校验 |
| 数据流 | 「X 产出 …，被 Y 消费」 | 解析器产出 AST，被优化器消费 |
| 控制 | 「X 决定 Y 是否/何时执行」 | 调度器决定任务何时进入执行队列 |
| 约束 | 「X 的 … 限制了 Y 的选择」 | 事务隔离级别限制了并发策略 |
| 替代 | 「X 与 Y 解决同一问题，代价不同」 | 轮询与长连接 |
| 演化 | 「X 在版本 … 被 Y 取代/包裹」 | 同步客户端被异步客户端包裹 |
| 反馈 | 「X 的结果反过来影响 X 的输入」 | 重试放大下游负载 |

每条边建议记六元组：

```text
from → to | 类型 | 因果短语 | 强度（强/弱） | 频率（每次/偶发） | 证据（源码/文档/实验）
```

**删边测试**：假设删掉这条边，是否至少有一个读者问题变得无法回答？

- 会 → 这是**承重边**，必须进正文，并在对应章节交代因果。
- 不会 → 装饰边，删掉，不要画进总图。

### 4.4 主干叙事线（spine）

spine 是全书的一句话论证结构，不是目录。

格式：

```text
为了让 <读者> 能 <完成目标>，
必须先解决 <问题 1>，因为它决定了 <约束 1>；
在此约束下，<问题 2> 只能通过 <机制 2> 解决；
但 <机制 2> 引入了 <新问题 3>，于是需要 <机制 3>；
最终这些选择共同导致 <整体行为/代价>。
```

四个检验：

1. **必要性**：每一环都说得出「为什么不能跳过」。
2. **顺序性**：交换任意两环，论证是否断裂？不断裂说明顺序是目录排序，不是叙事线。
3. **可复述**：读者读完后能用 5 句话复述。
4. **可落地**：每一环能映射到 1–2 章，且章内有对应断言。

spine 与目录的关系：**spine 决定顺序，模块树决定颗粒，切面决定内容。**

### 4.5 地图怎么产出（五步）

```text
G1 放节点：把 01-module-tree 的 L2 模块原样放上图，不新增、不改名（禁止幽灵节点）。
G2 抽边：从四类证据抽——接口/调用（源码或文档）、数据契约、故障传播、版本变更记录。
G3 找结构特征：扇入/扇出 Top 3（枢纽）、桥接节点（去掉后图断裂）、环（反馈）、孤岛（拆错或边界）。
G4 写 spine：按 4.4 格式写，再回头检查每个模块是否在 spine 上有位置；没有位置的模块要么降级，要么补进叙事。
G5 做映射：每条承重边标注「在哪一章哪一节交代」，形成地图-正文对照表。
```

结构特征的处置：

- **枢纽模块**：给更高篇幅、独立深潜章、更完整的失败模式。
- **桥接模块**：必须讲清「两边为什么需要通过它」，这是跨章因果的最佳落点。
- **环**：在正文明确标注「这是回路」，不要伪装成单向依赖。
- **孤岛**：若不是边界对象，回到 A1 重拆。

### 4.6 地图怎么在书里体现

| 位置 | 必须写什么 | 反例 |
|---|---|---|
| `ch00` 导读章 | 一句话定位、V1、V2、3 条关键场景、spine 图、3 条阅读路线、模块-章节-问题表 | 只有一张架构图 + 目录 |
| 每章开头（3 句） | 上游是谁（依赖什么）、本章改变什么、下游谁依赖它 | 「本章我们将学习……」 |

| 枢纽章 | 单独标注「本章是全书枢纽，改动会影响 …」 | 与普通章同样篇幅 |
| 附录 | 全局关系表 + 术语表 + 「改 X 影响 Y」变更影响表 | 只有术语表 |

**导读章的阅读路线**至少三条：

- 应用路线：只读应用线即可完成任务的章节序列。
- 原理路线：只读原理线即可建立机制图景的章节序列。
- 完整路线：默认顺序。

三条路线都从 `ch00` 出发，且每条路线上的跨章引用必须自洽（不能要求读者先读另一条线上的章）。

## 5. A3 深：单模块分析的标准动作

### 5.1 四层结构

每个 L2/L3 模块都按同一顺序分析，但**不是每层都写进书**——分析可以深，呈现按读者目标裁剪。

| 层 | 名称 | 回答 | 典型篇幅 | 写不写进书 |
|---|---|---|---|---|
| **C** | 概念层 | 它是什么、解决什么问题、边界在哪 | 300–600 字 | 必写 |
| **P** | 原理层 | 它为什么能工作、为什么必须这样设计 | 800–2000 字 | 必写（可按深度分级） |
| **D** | 分解层 | 它内部还能分成哪些子机制 | 每子机制 300–1500 字 | 按递归条件 |
| **E** | 证据层 | 凭什么相信：源码、公式、基准、案例 | 按需，单节 ≤50% | 关键断言必写 |

顺序不能颠倒：**先概念后原理，再分解，证据服务于断言**。反过来会写成「源码逐行注释」或「论文摘要」。

### 5.2 概念层：五步，避免词典式定义

词典式定义的典型句式是「XX 是一种用于……的技术」。它告诉读者**词义**，不告诉读者**判断力**。五步替代方案：

| 步骤 | 动作 | 写法示例（以「依赖注入」为例） |
|---|---|---|
| 1 触发问题 | 先展示「没有它会怎样」 | 当三个模块都要用同一个数据库连接，而连接配置又要能替换时，硬编码会让测试无法隔离 |
| 2 最小定义 | 一句可操作定义 + 判定判据 | 依赖注入是「由外部把依赖传入，而不是内部创建」；判据：把构造参数换成接口实现，对象行为是否随之改变且无需改内部代码 |
| 3 近邻对照 | 与 2–4 个易混概念划界 | 与「服务定位器」「工厂模式」「全局单例」对比：谁负责选择、谁负责生命周期 |
| 4 正反例 | 一个正例 + 一个反例，读者能自己判断 | 正例：构造函数注入；反例：在方法内 `new PgClient()` 后仍称其为注入 |
| 5 代价与边界 | 它让你付出什么、什么时候不该用 | 增加一层间接与配置复杂度；依赖极稳定时可能得不偿失 |

**四条硬规则**：

1. 不以「XX 是一种……」开头。改为「当……时，XX 保证……；代价是……」。
2. 定义必须**可判定**：读者拿一个例子能回答「是/不是」。
3. 必须给**反例**或**近邻对照**，否则概念没有边界。
4. 首次出现给**最小可用模型**，不要一次讲尽；后面用螺旋式回访加深（见 6.2）。

**概念卡**（每个模块 2–6 张）：

```markdown
### 概念卡：<术语>
- 一句话：当 <情境> 时，它保证 <结果>；代价是 <约束>。
- 判定：<读者可用的 yes/no 判据>
- 易混：<A>（差别：...）、<B>（差别：...）
- 正例：<...>
- 反例：<...>
- 首次出现：ch03 §3.1
- 回访：ch07 §7.4（加深）、ch12 §12.2（综合）
```

### 5.3 原理层：四件套 + 三问

原理不是「实现步骤」，而是**因果结构**。每个原理层至少包含：

1. **因果链**（≥3 环）：`因为 A，所以必须 B；否则 C；B 又引入 D，因此需要 E`。每环都要能指向证据（源码/文档/实验）。
2. **机制图**：状态机、时序图、数据流图三选一（按机制类型），图中每个节点在正文有对应解释，不做装饰。
3. **不变量**：无论实现怎么换都必须成立的约束。例：「任何时刻只有一个写者」「校验必须发生在副作用之前」「索引与数据在同一事务可见性下更新」。
4. **权衡表**：设计选择 × 替代方案 × 代价 × 适用条件。

再加**失败条件**：在什么输入、规模、并发、版本下该机制失效。没有失败条件的原理，通常还没讲透。

**三问检验**（每个原理段自检）：

- 为什么需要它？（没有它，哪个具体问题无解）
- 为什么是这个顺序/结构，而不是另一种？（顺序错误会怎样）
- 换一种做法会怎样？（替代方案的代价，直接连到权衡表）

**原理深度分级**：

| 级别 | 内容 | 适用 |
|---|---|---|
| P1 现象级 | 观察到什么、输入输出关系 | 入门章、应用线 |
| P2 机制级 | 关键数据结构、控制流、不变量 | **默认** |
| P3 实现级 | 源码路径、并发原语、内存布局 | 核心章、枢纽模块 |
| P4 形式化级 | 复杂度证明、协议规约、正确性论证 | 研究型/综述型 |

默认写到 P2；核心章到 P3；只有明确面向研究者时才到 P4。**深度分级要写进模块规格**，否则每章会随机深浅。

### 5.4 分解层：递归与停止条件

递归不是「越深越好」，而是**按读者目标付费**。

**什么时候递归**（满足任一）：

- 子机制本身是读者的目标（例如讲 React，Fiber 调度就是目标之一）。
- 子机制是理解父机制的必要前提（不拆读者无法建立因果链）。
- 子机制是高频故障点（不拆无法写清陷阱）。

**递归怎么写**：

- 每层重复 `C 概念 → P 原理 → D 分解`，但篇幅递减：子层总篇幅 ≤ 父层的 60%。
- 每层最多 2–5 个子项；超过先分组，不要平铺。
- 递归必须回到父层：写完子机制，用一句话说明「它如何支撑父机制的不变量/因果链」。

**五个停止条件**（满足任一即停）：

| 编号 | 停止条件 | 判断问句 |
|---|---|---|
| S1 | 目标到达 | 读者已能完成模块承诺的动作/判断？ |
| S2 | 同质重复 | 继续拆只是同一机制换参数/换 API？ |
| S3 | 前置越界 | 再拆需要另一本书、另一领域的前置知识？ |
| S4 | 证据不足 | 没有源码/文档/论文/实验可支撑，只能猜？ |
| S5 | 边际收益不足 | 新增理解 < 新增术语与认知成本？ |

**深度预算**：全书默认最深 3 层（模块 → 机制 → 子机制）；枢纽模块可到 4 层，但必须在 `04-dual-track.md` 写明理由与预算。超过预算的内容放附录或"延伸阅读"，不塞进正文。

### 5.5 四层写法差异

| 维度 | 概念层 C | 原理层 P | 分解层 D | 证据层 E |
|---|---|---|---|---|
| 目的 | 建立判断力 | 建立因果模型 | 定位到可理解单元 | 让断言可信 |
| 主语 | 读者/问题 | 机制/约束 | 子机制 | 源码/实验 |
| 典型句式 | 「当……时，它保证……；代价是……」 | 「因为……所以必须……；否则……」 | 「这一层负责……，它把……变成……」 | 「在 v2.3 的 `src/x.ts:88`，……」 |
| 证据要求 | 正反例 | 机制图 + 不变量 | 接口/边界 | 可复现 |
| 失败信号 | 词典句式、无判据 | 只讲 what、无权衡 | 无限展开、不回链 | 大段代码无解释 |

## 6. A4 织：双线并行（定稿模型）

### 6.1 两条线各自负责什么

| | 应用线 | 原理线 |
|---|---|---|
| 回答 | 怎么用、什么时候用、参数怎么选、边界在哪、坏了怎么查 | 为什么必须这么用、内部机制、数据结构、算法、设计取舍 |
| 读者状态 | 要完成任务 | 要建立机制图景 |
| 写法 | 场景 → 步骤 → 参数 → 边界 → 排错 | 机制 → 因果链 → 不变量 → 权衡 → 失败条件 |
| 原理含量 | 低：只给**最小必要解释** | 高：P2–P4（见 5.3） |
| 证据 | 可运行代码、配置、命令、输出 | 源码、图、公式、基准、协议 |
| 不做什么 | 不展开推导、不讲设计史 | 不重复贴完整用法、不写成 API 清单 |

**关键约定**：两线不是「两种段落」，而是**两个可独立成立的叙述**。同一模块写两遍不是浪费——应用线回答「手怎么动」，原理线回答「为什么这样动不会坏」，两者的信息不重复，只是指向同一对象。

**轨道归属判据**：`track` 标记是给 `ratio-count` 记账用的，依据是**内容性质**，不是段落所在的编号位置，也不是写作顺序。常见错误是「从现象定位机制」的推理被写成原理，或机制解释顺手留在综合段，结果综合段虚高、原理线偏低。按四条判：

| 写的是 | 归到 | 例 |
|---|---|---|
| 机制与因果链、对象结构、数据结构/算法 | `principle` | 模型字符串如何解析成实例；Profile 与实现的交集 |
| 判断顺序、排错决策、成本来源与取舍 | `principle` | 先看消息序列还是先改提示词；读源码与版本说明的成本 |
| 双向映射：操作或现象 → 机制 → 所以 → 不这样会怎样 | `synthesis` | 「字段齐全但不合法」→ 校验器缺位 → 所以要补校验 |
| 深度判断、误区、选型结论 | `synthesis` | 「缺省键不是不支持」「声明支持不等于一定可用」 |

一段里混着两类内容就按句拆开归位，不要整段硬塞。补论述修「表格替代论述」时尤其容易把机制写成综合段；补完用 `ratio-count` 复核两件事：被修小节成段论述 ≥120 字，且综合段占比没有因此虚高（>15%）。若只靠挪位置无法同时满足，优先保证内容性质正确，再如实报告比例。

### 6.2 章内固定顺序：应用 → 原理 → 综合

每一章（L2 模块）固定三段，顺序不改：

```text
┌─────────────────────────────────────────────┐
│ 章首：位置声明 + 双线目标（3–5 句）            │
├─────────────────────────────────────────────┤
│ 第一段  应用线  N.1 – N.k                     │
│   场景 → 最小可用路径 → 参数/配置 → 边界 → 排错 │
│   （原理只给"最小必要解释"，标注 [原理见 N.m]）  │
├─────────────────────────────────────────────┤
│ 第二段  原理线  N.k+1 – N.p                   │
│   概念锚定 → 机制与因果链 → 数据结构/算法      │
│   → 设计取舍 → 失败条件                       │
│   （引用应用线时一句话复述，不假设读者刚操作过） │
├─────────────────────────────────────────────┤
│ 第三段  综合    N.p+1 – N.q                   │
│   双向映射表 → 何时必须深挖/何时照用就够        │
│   → 常见误区 → 章末双线索引                    │
└─────────────────────────────────────────────┘
```

**为什么是这个顺序**：先给可执行路径，读者获得「这东西能干什么」的锚点；再讲机制，机制就有了挂靠点；最后做映射，把操作与机制扣在一起。对应用型读者，读完第一段即可收工；对原理型读者，第一段是问题背景，第二段才是正文。

**章首不属于任何一条线**：它只有 3–5 句导航（位置、目标、只读建议），不承担操作步骤，也不展开机制。

**不采用分卷式或主线深潜式作为默认**：本书要求每一章都能同时交付「能上手」与「能解释」两种价值；把两线拆成前后两卷，会让原理卷失去问题锚点、应用卷失去边界解释。分卷只在一种情况下考虑：读者分层极端明显且用户明确要求（例如「入门版 + 原理版」两本书），这属于产品决策，不是默认编排。

**概念层怎么放**（容易写错的地方）：

- 应用线开头给**工作定义**（1–2 句，够用即可），例如「连接池就是一组可复用的已建立连接」。
- 原理线开头做**完整概念锚定**（5.2 的五步：触发问题、可判定定义、近邻对照、正反例、代价边界）。
- 两处定义必须一致，但详细程度不同；原理线的定义是权威版本，应用线的工作定义要加「详见 N.m」。

### 6.3 综合段：双向映射，不是复述

综合段要完成四件事，缺一不可：

**（1）双向映射表**：把应用线的操作/现象回指到原理线的机制。

| 应用线的操作/现象 | 原理线的机制 | 所以（为什么快/安全/省/稳） | 不这样会怎样 |
|---|---|---|---|
| 复用连接而不是每次新建 | 三次握手 + 慢启动成本 | 避免每次请求付握手与拥塞窗口重建成本 | 高 QPS 下连接建立成为瓶颈，尾延迟抬升 |
| 先校验再落库 | 校验必须在副作用之前的不变量 | 失败请求不产生脏数据，重试幂等 | 半成功状态需要人工修复 |
| 超时设置小于上游预算 | 超时是预算的分解，不是独立参数 | 避免下游慢拖垮整条链路 | 重试叠加导致雪崩 |

规则：

- 应用线每个**关键步骤**至少映射到一条机制；原理线每条**承重机制**至少映射到一个操作或一个边界。
- 映射列必须写「所以」，不能只写「对应关系」。写不出「所以」，说明原理线没讲清或不相关。
- 「不这样会怎样」列是陷阱章的素材来源。

**（2）何时必须深挖 / 何时照着用就够**：

| 必须深挖原理的信号 | 照着用就够的信号 |
|---|---|
| 默认配置达不到性能/成本目标 | 标准用法、默认参数在预算内 |
| 出现非预期行为（延迟抖动、偶发失败、数据不一致） | 行为符合文档承诺，无可观测异常 |
| 要跨版本迁移或替换实现 | 版本稳定，无迁移计划 |
| 高并发、多租户、强一致等约束叠加 | 单机、低负载、弱约束 |
| 安全、合规、审计要求可解释性 | 内部工具、可回滚、影响面小 |
| 要做架构决策或技术选型 | 只在既有架构内填空 |

这张表直接回答读者「我到底要不要读原理线」，也是双线可读性的核心保障。

**（3）常见误区**：3–5 条，每条写「现象 → 根因（回指机制）→ 正确做法」。

**（4）章末双线索引**：

```text
应用要点：<3–5 条，能直接照做>
原理要点：<3–5 条，能复述机制>
交叉点：<哪几个操作由哪条机制解释>
```

### 6.4 对位规则：书 / 章 / 节 / 句

| 层级 | 对位要求 | 落地方式 |
|---|---|---|
| **书级** | 应用能力清单与原理断言清单**互相覆盖** | `04-dual-track.md` 两张清单，逐条编号 A-01/P-01，互相标注 |
| **章级** | 每章声明 `appTarget`（能做什么）与 `principleTarget`（能解释什么） | 章首 callout；frontmatter 两个字段 |
| **节级** | 每个原理节标注「解释哪几个应用节」；每个应用节标注「原理见哪节」 | 节首一行 `> 原理对应：N.5`；应用节末 `> 原理见 N.5` |
| **句级** | 应用断言带「因为」锚点；原理断言带「所以」落点 | 行内链接：`（因为连接复用有半开风险，见 §N.6）` |

节级编号建议固定：

- 应用节：`N.1`、`N.2`……（A 系列）
- 原理节：`N.4`、`N.5`……（P 系列）
- 综合节：`N.8`、`N.9`（S 系列）

编号不要求连续语义，但**一旦在 `04-dual-track.md` 登记，就不再变动**，否则交叉引用会漂移。

### 6.5 断点测试：两条线各自能读通

「断点测试」是在**任意一条线结束时合上书**，检查读者是否仍然成立。测试必须在写作后执行，并把结果记进 `04-dual-track.md`。

#### 测试 A：只读应用线

**做法**：从章首读到应用线结束（N.k），跳过所有原理节与「原理深潜」块，尝试完成 `appTarget`。

| 检查项 | 通过标准 | 常见失败 |
|---|---|---|
| 任务闭环 | 能按步骤得到一个可验证结果 | 步骤依赖原理节才给出的参数 |
| 代码可运行 | 依赖、版本、入口、预期输出齐全 | 缺环境变量、缺初始化 |
| 参数可决策 | 每个关键参数有默认值/范围/影响 | 只写「按需配置」 |
| 术语自足 | 应用线使用的术语都有工作定义或术语表链接；未定义术语 ≤2 | 突然出现「背压」「不变量」却不解释 |
| 边界可见 | 写明不适用场景与至少 3 个失败信号 | 只讲 happy path |
| 排错可用 | 至少 3 类常见错误的定位与处理 | 「请检查日志」 |
| 不依赖原理假设 | 凡是必须遵守的规则，都以**规则句**写出，而不是「因为机制如此」 | 「这里必须加锁（原因见后文）」 |

**关键判据**：把原理线整段删掉，应用线仍然是一篇可交付的操作指南。

#### 测试 B：只读原理线

**做法**：从章首（或原理线起点）读，跳过应用线的操作正文；允许把应用线代码当作**展品**看，但不要求读者执行过。

| 检查项 | 通过标准 | 常见失败 |
|---|---|---|
| 概念完整 | 有完整概念锚定（5.2 五步），不是工作定义 | 直接进入源码 |
| 因果闭合 | 因果链从问题到机制到代价完整，≥3 环 | 「然后调用 X」式步骤复述 |
| 证据可查 | 每个关键断言有源码/文档/论文/实验 | 「显然」「一般来说」 |
| 不依赖操作 | 引用应用步骤时，用一句话复述该步骤是什么 | 「如上例所示」 |
| 符号自足 | 公式/图中符号在首次出现处解释 | 裸公式 |
| 可重建图景 | 读者能凭记忆画出机制图，并说出不变量 | 只有零散知识点 |
| 失败条件 | 写出机制在什么条件下失效 | 只讲成功路径 |

**关键判据**：把应用线的操作步骤整段删掉，原理线仍然是一篇可独立阅读的机制说明。

#### 测试 C：只读综合段

综合段应能独立回答三个问题：这条操作由什么机制解释？我什么时候必须深挖？最常见的误区是什么？若必须回读前文才能理解综合段，说明映射表写成了复述。

#### 量化护栏

| 指标 | 下限/上限 |
|---|---|
| 每章端到端应用任务 | ≥1 个 |
| 每章失败/排错路径 | ≥3 类错误 |
| 每章机制图 | ≥1 张（原理线） |
| 每章不变量 | ≥1 条 |
| 每章权衡表 | ≥1 张（可为小表） |
| 应用线未定义术语 | ≤2 个，且必须在术语表 |
| 原理线前向引用 | 每节 ≤2 个，且给最小解释 |
| 长代码重复 | 0：原理线引用行号或短摘录，不整段重贴 |

### 6.6 比例与篇幅

#### 6.6.0 全书总量与章长分配（先定总量，再谈比例）

篇幅不由「每章固定预算」反推。A0/A1 之后按三个变量定全书 CJK 总量（`body3` 口径：不含 `meta`，只算正文，表格按 1/2 计数）：

```text
总量目标 = 模块数 × 平均递归深度 × 概念密度系数
```

概念密度系数按技术类型取参考区间：

| 技术类型 | 特征 | 合理区间（CJK） |
|---|---|---|
| 纯库 / 框架 | API 面明确，概念可枚举 | 6–10 万 |
| 语言 / 规范 | 语义细节多、边界与陷阱密集 | 8–14 万 |
| 系统 / 平台 | 跨组件协作、部署与故障面广 | 10–18 万 |
| 应用 / 教程型 | 以任务链为主，原理线较薄 | 5–8 万 |

三条约束：

1. **下限 5 万 CJK（`body3`）**：这是底线，不是目标。达不到说明覆盖不全，不是「写得精简」。
2. **上限不设死线**：以覆盖度为准——每个 L2 模块是否讲到读者能独立判断与操作。超出同类参考区间时，必须在 `04-dual-track.md` 或大纲写下「为什么这个内容量必要」（如概念密度高、失败面广、源码证据多），不能用比例或预算反向砍内容。
3. **章长按模块权重分配，不平均**：权重 = 模块复杂度 × 读者依赖度 × 概念密度（各 1–3 分）。重章可 8 千，边缘章可 3 千；同层最大/最小比不超过 3:1。大纲里的「预估字数」是分配结果，不是配额。

**字数口径（唯一）**：只统计正文 CJK，剔除围栏代码块、HTML 注释与 `meta`（章首 / `N.0` / `N.10`）；Markdown 表格按 1/2 计数（表内 CJK × 0.5），表格以外的成段文字按 1:1 计数。`ratio-count.mjs` 与 `word-count.mjs` 共用 `scripts/lib/word-caliber.mjs`。**表格不能替代论述**：每个 H2 小节都要有成段文字讲清因果与取舍；脚本对「有表但成段论述 <120 字」或「表格折算占比 >60% 且成段论述 <300 字」的小节报 WARN。5 万下限只约束 `body3`，不允许靠堆表格补足。

比例**只做事后校准，不做事前配额**。下表的占比是诊断参考，不是写作时逐节配平的目标：

| 段落 | 参考区间 | 说明 |
|---|---|---|
| 章首位置声明 + 双线目标（`meta`） | 3%–5% | 不超过 300 字，不参与比例 |
| 应用线 | 35%–55% | 按对象类型取 2.4 的比例 |
| 原理线 | 30%–55% | 核心章可上浮，工具章可下探 |
| 综合段 | 10%–15% | 低于 10% 通常映射不完整；高于 15% 通常在复述 |

2.4 的比例指**应用线与原理线之间**的相对占比（不含综合段）；换算成整章占比时，两条线合计约 85%–90%。比例按**中文正文 CJK**统计：剔除代码块、示意输出与 HTML 注释，表格内 CJK 按 1/2 计入。

#### 6.6.1 目标值与实测值分开

| 值 | 写在哪 | 谁写 | 什么时候 |
|---|---|---|---|
| **目标比例** | `04-dual-track.md` 章级对位表的「目标比例」列；该表缺省时取同文件「应用 : 原理 = X : Y」一行 | 规划者 | 阶段 2，与大纲同时定 |
| **实测比例** | 章节 frontmatter 的 `ratio` | `scripts/ratio-count.mjs --write` | 阶段 3 完稿后、阶段 6 质检前 |

写作过程中**不要填 `ratio`**。写作时无法测量，先填只会制造一个看起来精确、实际靠猜的数——上一版方法论正是这样，三张样章分别写了 55:45、40:60、60:40，但没有任何手段验证它们。

#### 6.6.2 轨道标记

正文在每个 H2 标题的上一行（允许中间空行）单独放一条 HTML 注释：

```markdown
<!-- track: app -->
## 3.1 应用场景：从客服对话到工单对象
```

取值只有四个：

| 标记 | 含义 | 参与比例 |
|---|---|---|
| `app` | 应用线 | 是 |
| `principle` | 原理线 | 是 |
| `synthesis` | 综合段 | 是（单独算占比） |
| `meta` | N.0 本章位置/前置约束、章末延伸阅读、阅读路线 | 否 |

规则：

1. **粒度是 H2**。H3 及以下继承所属 H2 的轨道，不重复标记。
2. 每个 H2 恰好一条标记；缺失即报错。
3. 同一轨道可以连续出现在多个 H2 上（例如 N.4–N.7 各标一次 `principle`），不需要合并。
4. 第一个 H2 之前的内容（H1 标题、「本章怎么读」callout）自动归 `meta`，不需要标记。
5. 标记会被 HTML 注释规则吞掉，不影响 MDX/LaTeX/EPUB 渲染，也不进入成书。

#### 6.6.3 测量脚本

`scripts/ratio-count.mjs`：

- **输入**：`mdx/*.mdx`、`metadata/analysis/04-dual-track.md`（章级目标 + 书级默认）、`metadata/outline.md`（兜底取「应用:原理」列）
- **计算**：按 H2 切段 → 剔除代码块与 HTML 注释 → 表格行与成段文字分开统计 → 表内 CJK × 0.5、其余 1:1 → 按轨道求和
- **输出**：`metadata/ratio-report.txt`，含逐章 应用/原理/综合/meta 字数、表格折算字数、实测比例、目标、偏差（百分点）、全书合计，以及 `body3` 是否达到 5 万下限
- **判定**：
  - 缺轨道标记 → ERROR
  - 应用线占比相对目标偏差 > 10pp → WARN
  - 综合段占比不在 10%–15% → WARN
  - 某 H2 有表但成段论述 <120 字，或表格折算占比 >60% 且成段论述 <300 字 → WARN（表格不能替代论述）
  - 默认不阻断构建；`--strict` 时 ERROR 导致退出码 1
- **`--write`**：把实测比例回写各章 frontmatter 的 `ratio: "A:P"`

阈值可调：`--threshold=8`、`--synth-min=8 --synth-max=18`、`--min-body=40000`；表格/论述 WARN 的阈值固定为 120 / 60% / 300，与 SKILL 阶段 4 一致。

#### 6.6.4 偏差怎么处理

偏差超过阈值不等于「要改字数」，先判断属于哪一类：

| 情况 | 处理 |
|---|---|
| 原理线确实需要展开（枢纽章、机制章） | 保留，在 `04-dual-track.md` 写明「本章原理线 52%，理由：…」 |
| 应用线里塞进了原理内容 | 移到原理线，而不是删掉 |
| 综合段 > 15% | 通常是在复述：先删掉与前文重复的行，保留映射与判断。若是为修「表格替代论述」而补的成因/取舍/失败模式，**不算复述**：保留并在 `04-dual-track.md` 记录理由，不得为回区间删论述 |
| 综合段 < 10% | 映射表行数不足，或缺「何时深挖」判断表 |

一句话：**偏差是诊断信号，不是及格线。**

节数可按模块规模压缩：小章可合并为 `N.1 应用`、`N.2 原理`、`N.3 综合` 三节，但**三段顺序、内容职责与轨道标记不变**；合并后仍是三条标记，不能只标一条。

#### 6.7.1 图位标注语法与可渲染源

图位注解不是占位符，而是「图号 + 类型 + 内容 + 依据 + 可渲染源」的绑定。注解后必须紧跟真实图片引用和加粗图题：

```markdown
<!-- FIGURE: fig-12-1 | architecture | 三种连接与信任边界 | 依据 12.2.4 与 12.4.5 -->

![图 12-1　三种连接与信任边界](/figures/fig-12-1.svg)

**图 12-1**　三种连接与信任边界
```

| 字段 | 规则 |
|---|---|
| `id` | `fig-NN-M`：NN 为两位章号，M 为章内序号；与 frontmatter `figures` 一一对应 |
| `type` | 只能取 `architecture` / `flowchart` / `sequence` / `state-machine` / `decision-tree` / `timeline` / `matrix` / `layered` |
| `内容` | 一句话说清图要表达什么，不写「示意图」这类空话 |
| `依据` | 指向支撑该图的节号、表号或实测输出，便于复核 |
| 图源 | HTML 源 `mdx/public/diagrams-src/<id>.html`；用 `assets/diagram-style/export_svg.py --system-fonts` 导出 |
| 产物 | `mdx/public/figures/<id>.svg`（或 `.png`），正文必须用 `![...](/figures/<id>.svg)` 引用 |
| 图题 | 注解后 4 行内必须出现 `**图 N-M**　<标题>`，不再写「待绘制」 |

**配图触发规则**：一个 H2 涉及 ≥3 个对象且存在先后、分层、分支或状态迁移时，必须配图；每章硬下限 2 图；禁止为凑数画装饰图。

**来源优先级**：diagram-design 的 HTML→SVG 为主路径；mermaid/plantuml 围栏保留兼容。围栏前 5 行有 `<!-- FIGURE: fig-NN-M ... -->` 时，`diagram-renderer.mjs` 输出稳定图号；否则沿用旧 hash 命名，旧书不受影响。

frontmatter 的 `figures` 列表与正文图位 id 必须**集合相等、无重复**，且每个 id 都能在 `figures/` 找到产物。`scripts/render-figures.mjs` 负责导出与引用检查，`scripts/chapter-lint.mjs` 负责一致性校验（8.8）。

#### 6.7.2 章末参考小节（N.10）

- 独立成节，不并入 `N.9`；`track: meta`。
- 每条写三件事：参考了什么、提供了什么、与本章哪一节/哪个结论相关。
- 只描述资料贡献，不点评资料瑕疵；不出现「你提供的文档有偏差」「原文写法有误」这类表述。
- 篇幅控制在 3–5 条，避免变成文献综述。

### 6.9 A4 的输入、产出与 DoD

### 6.10 双线反模式

| 反模式 | 表现 | 修法 |
|---|---|---|
| 伪双线 | 应用段里塞满原理，原理段重复应用 | 应用段只保留「规则句」；原理段只保留机制与证据 |
| 复述式总结 | 总结 = 应用要点 + 原理要点各抄一遍 | 强制写映射表「所以/不这样会怎样」两列 |
| 原理前置 | 章首先讲 2000 字机制，读者不知道有什么用 | 把机制移到第二段；章首只留位置声明与目标 |
| 代码双份 | 应用线和原理线各贴一遍完整代码 | 原理线只贴关键行 + 行号 |
| 术语暗礁 | 应用线用「背压」「幂等」「不变量」不解释 | 工作定义或术语表链接；未定义术语 ≤2 |
| 深挖上瘾 | 每章都递归到源码，读者失去主线 | 按 5.4 停止条件裁剪，深度写进预算 |
| 总结过长 | 综合段占 30%，变成第三遍讲解 | 压到 10%–15%，只做映射与判断 |

### 6.11 四条写作硬规则

这四条与双线编排并列，阶段 3 写作时必须执行；阶段 6 由 `chapter-lint.mjs` 与人工复核兜底。

| 规则 | 做法 | 反例 | 检查 |
|---|---|---|---|
| 正文不点材料 | 只陈述事实与结论；参考内容统一放 `N.10 本章参考`，写清「提供了什么 / 与本章关系」 | 「你提供的文档这里有偏差」「原文写法有误，实际是……」 | R1 禁语扫描（WARN + 人工复核） |
| 多配图 | 一个 H2 涉及 ≥3 个对象且存在先后/分层/分支/状态迁移时必须配图；每章 ≥2 图；不为凑数画装饰图 | 整节纯文字堆叠；为满足数量画一个只有标题的装饰框图 | F1 图产物 + 每章下限；人工判断触发条件 |
| 代码中文注释 | 关键行、关键参数用中文注释说明意图；不逐行注水 | 50 行代码零注释；每行都加「# 赋值」 | C1 代码块中文注释（WARN） |
| 公式中文说明 | 每个块级公式后逐个解释符号含义，并说明式子描述什么关系 | 只贴公式不解释；解释只说「如上式」 | M1 公式后说明（WARN） |

**证据等级配套**：正文断言强度不得超过该代码块的验证等级。L1 只陈述导入/语法通过；L2 只陈述跑通（含测试模型等离线路径）；L3 才能陈述行为结论。逐块记录写 `metadata/verify/chNN.txt`。

### 7.5 借用边界：三条自律规则

1. **一个理念只指定一个主责步骤**；其他出现只能作为该步骤的约束或检查项，不得反向改写别的步骤。例如认知负荷的主责步骤是 A4（6.2 的应用先行），它在 A1 粒度与 A4 断点测试中只是约束。
2. **必须有可观测产物**。产物可以是表格字段、检查项、模板段落；不能只是「要有系统思维」。
3. **冲突时以读者任务优先**。理论之间会打架：螺旋课程要求回访，认知负荷要求少重复；MECE 要求穷尽，篇幅要求裁剪。解决顺序是：读者终点能力 > 认知负荷 > 结构完整性 > 理论纯粹性。

**明确不借用的东西**：

- 不引入「学习风格」（视觉型/听觉型）——缺乏稳定证据，且会把双线误做成「图给视觉读者、文字给阅读读者」。
- 不把系统论当隐喻写进正文（「软件是一个生态系统」）——只在分析阶段使用。
- 不追求「知识全覆盖」——MECE 是对**本书边界内**而言，不是对学科而言。

## 8. 落进 cookbook-forge：各阶段怎么接

### 8.1 总原则

**不新增「第七阶段」**。把 A0–A4 挂进现有阶段 0–2，让分析产物成为阶段 3 的**写作规格**；阶段 4–6 只增加检查，不改变工具链。

对应你关心的五个环节：**材料解析 = 阶段 0–1；章节规划 = 阶段 2；写作 = 阶段 3；模板渲染 = 阶段 5；质检 = 阶段 6**。

```text
阶段 0 输入识别 ──> +A0 对象判定 ──> metadata/analysis/00-object.md
阶段 1 资料采集 ──> +A1 证据矩阵 ──> 02-evidence-matrix.md（按切面补资料）
阶段 2 大纲设计 ──> +A1 拆解 +A2 地图 +A4 双线 ──> 01/03/04 + outline.md
阶段 3 逐章写作 ──> 按 04 与 05-module-specs 写，章内 应用→原理→综合
阶段 4 篇幅校准 ──> 按覆盖缺口补，比例只做诊断，不按总字数硬凑
阶段 5 格式转换 ──> 结构映射（标题层级/交叉引用/callout）
阶段 6 交付 ──> 增加内容质检与断点抽检
```

### 8.2 阶段 0：输入识别 → 增加对象判定

现有阶段 0 已收集主题、资料、读者、字数、格式。新增三个问题（合并进现有 `AskUserQuestion`，不额外增加轮次）：

1. **这本书主要是「讲清一个机制」还是「教会一个工具」？**（用于区分 T1/T2，允许混合）
2. **读者读完后要能独立完成哪 3 件事？**（终点能力，直接进 `00-object.md`）
3. **本书明确不覆盖什么？**（边界，防止范围蔓延）

产出：`metadata/analysis/00-object.md`（模板见 2.8）。

**DoD**：2.7 的五条全部满足，且用户确认过「不承诺」清单。

### 8.3 阶段 1：资料采集 → 按切面建证据矩阵

现有阶段 1 是「穷尽式采集 + 每条资料记录 URL/标题/作者/日期/使用章节」。增加两件事：

1. **按切面补采**：主切面与辅助切面确定后，检查每个切面是否有足够证据。缺证据的切面，要么补采，要么从方法论中降级（不要硬写）。
2. **标注支撑对象**：每条资料除了「使用章节」，再标 `supports: M03, M07` 或 `supports: P-02`，形成可反查的证据矩阵。

产出：`metadata/analysis/02-evidence-matrix.md`

```markdown
# 证据矩阵

| 切面 | 需要的证据 | 已有来源 | 支撑模块 | 缺口 | 处置 |
|---|---|---|---|---|---|
| F01 层次 | 官方架构文档、入口源码 | S3, S7 | M01–M05 | 无 | - |
| F04 生命周期 | 时序说明、trace | S9 | M03 | 缺峰值场景 | 补压测报告 |
| F12 失败模式 | issue/故障复盘 | 无 | M06 | 严重 | 补 issues 检索，否则降级为「已知限制」 |
```

**DoD**：主切面与辅助切面无「严重缺口」；每个 L2 模块至少 1 条证据；每条关键原理断言至少 1 条可查来源。

### 8.4 阶段 2：大纲设计 → 用 spine 取代固定 15 章

这是改动最大的一步。

#### 现有做法的问题

固定 15 章骨架（全景→基础→快速开始→安装→核心概念→架构→模块→调用链→配置→Recipes→性能安全→测试→部署→生态→总结）是**T2/T4 的候选模板**，不是通用结构。直接套用会强迫 T1 写「安装」「部署」，强迫 T3 写「API 速查」。

#### 新做法（五步）

```text
2.1 跑 A1：产出 module-tree（含 MECE 记录）
2.2 跑 A2：产出 global-map（五视图 + spine）
2.3 跑 A4：产出 dual-track（比例、能力/断言清单、章级对位）
2.4 用 spine 排序模块，生成 outline：
    - 模块顺序 = spine 顺序（不是旧模板顺序）
    - 旧 15 章只作为"候选章"抽取，不要求全部出现
2.5 用户确认：module-tree + spine + outline 一起给用户
```

#### `outline.md` 新字段

| 字段 | 说明 | 示例 |
|---|---|---|
| `moduleId` | 对应模块树 id | `M03` |
| `objectType` | 本书主类型 | `T2` |
| `layer` | L1/L2 | `L2` |
| `question` | 本章回答的读者问题 | 请求卡在哪一层？ |
| `appTarget` | 应用线目标（可观测） | 能定位请求卡点 |
| `principleTarget` | 原理线目标（可解释） | 能解释各层顺序约束 |

### 8.5 阶段 3：逐章写作 → 章内固定三段

### 8.5.1 示例的验证等级（L1–L3）

「示例可跑」无法验收，拆成三级：

| 等级 | 含义 | 判据 | 正文允许的措辞 |
|---|---|---|---|
| **L1** | 导入与语法通过 | 文件能被解释器加载，构造语句不抛异常 | 「可以这样写」「参数形如」 |
| **L2** | 端到端跑通（离线路径） | 完整跑完一次并留下输出；通常用测试模型、内存服务器等 | 「跑通」「不报错」；**不得**断言行为 |
| **L3** | 行为可信 | 真实模型，或可验证的行为断言（输出结构、节点序列、异常类型） | 「实测输出为 …」「失败时报 …」 |

标注方式：python 围栏的上一行（3 行内）写一条注释：

````markdown
<!-- verify: L2 -->
```python
result = await agent.run("查一下 SKU-1 的库存")
```
````

规则：

1. **每个 python 块必须标**。配置示意（不执行）也标 L1，并在正文注明「未执行」。
2. **断言强度不得超过等级**。L2 块之后只能写「跑通」「不报错」；要写「模型会返回这样的 JSON」，必须有 L3 证据。
3. 同一块里既有可验证部分又有不可验证部分时，按**最低**等级标，并在正文点明哪部分未验证。
4. 升版本重跑后，等级可升可降，正文措辞随之改。

为什么需要这条：测试模型会生成占位参数，能跑通结构化输出、工具调用、MCP 延迟加载等路径，但**行为与真实模型不同**。上一轮三张样章里，第 6 章把「测试模型把工具返回值当最终输出」写成了通用结论，第 12 章用测试模型驱动 `defer_loading` 直接失败——两处都是把 L2 当 L3。

#### 逐块实测记录 `metadata/verify/chNN.txt`

每个 python 块一条记录，顺序与正文一致：

```text
# 验证记录 ch12
生成时间: 2026-11-07T13:40:57Z
环境: python x.y / yourlib x.y.z / model: test

## 块 1
file: examples/ch12_inmemory.py
verify: L2
status: OK
output:
discovered: [('stock', '查询指定 SKU 的库存数量。')]
output: {"stock":7}
usage: RunUsage(input_tokens=107, output_tokens=13, requests=2, tool_calls=1)
```

`status` 取值：`OK` / `FAIL` / `SKIP`（续写片段）/ `CONFIG`（配置示意，不执行）。`FAIL` 必须附异常类型与首行信息；`output` 原样抄录，不要美化对齐。

这份记录是「实测」的唯一凭据：正文改了预期输出却没更新记录，阶段 6 视为未验证。

**现有章节元素的去留**：

|---|---|

| 本章地图 callout | `N.0` 的「只读建议」 |

### 8.6 阶段 4：篇幅校准 → 按覆盖度补，比例只做诊断

现有阶段 4 的补足优先级是「Recipes → 源码/原理 → 配置/API → 对比/排障 → 附录」。比例报告只用来定位「某条线可能被代码或表格替代」，不是补写目标；先判断覆盖是否足够。不设逐章字数预算，也不为凑比例改内容。

| 缺口 | 补什么 | 不要补什么 |
|---|---|---|
| 应用线偏短 | 端到端任务、参数表、错误处理、迁移步骤 | 大段原理推导 |
| 原理线偏短 | 因果链补环、机制图、不变量、权衡表、失败条件 | 重复 API 说明 |
| 综合段偏短 | 映射表补行、判断表、误区 | 复述前文 |
| 某节有表但成段论述不足（`ratio-count` WARN） | 在该 H2 补成因、取舍、失败模式与判断顺序；删表后仍能独立读懂 | 给表加行、把表格单元格改写成句子、删表了事 |
| 两线都够但 `body3` 不足 5 万 CJK | 回 A1 检查是否漏了模块，或补附录（reference）；按覆盖缺口补 | 注水、重复、为凑数加装饰章节、靠加表格补字数 |
| 总量已超同类参考区间 | 先确认覆盖是否真的需要；确需则在 `04-dual-track.md` 写明理由 | 为「回到区间」删掉必要的失败面或证据 |

**DoD**：`metadata/ratio-report.txt` 已生成；每章两线比例偏差 >10pp 时有书面理由；全书 `body3` ≥5 万 CJK（只算正文：剔除代码块、HTML 注释、meta；表格按 1/2 计数）；每个 L2 模块达到「读者能独立判断/操作」的覆盖标准；超出参考区间有书面理由；「表格替代论述」WARN 已补成段论述并通过「删表可读」检查。补足后断点测试仍通过（补内容容易破坏自足性）。补完重跑 `ratio-count.mjs --write`，不要手改 `ratio`。补论述导致的综合段 >15% 属诊断信号：非复述则保留并记录，不按配额回删。

#### 新增人工闸门：断言强度

脚本能查标记，查不出「正文把 L2 说成了 L3」。阶段 6 逐段过一遍：

```text

[ ] 配置示意块（未执行）已标 L1，且正文写明「未执行」
```

这条闸门最容易漏，因为它读的是**措辞**而不是**结构**。建议用子 agent 单独跑：只给它章节正文与 verify 记录，不给写作过程，问它「哪些断言超出了记录能证明的范围」。

#### 新增制度闸门：脱敏与产物（提交前自查）

内容闸门管「书写得对不对」，制度闸门管「该不该进这个仓库」。两者都必须在提交前过，因为已推送的敏感内容只能靠重写历史清理。

**为什么**：Skill 仓库是公开分发单元。样书书名、模块包名、用户名、可反查的目录结构一旦进入工作区或历史，等于公开用户材料；PDF/EPUB 与三端构建目录体积大、无法评审，且会永久留在历史里。重写历史的代价是所有下游 SHA 变化、协作者需重新克隆、必须先做仓库外备份。所以这条规则的价值全在「提交前拦住」，而不是「事后清理」。

**怎么自查（三条全为 0 才允许 commit）**：

```bash
git grep -n -iE "<项目名>|<模块包名>|<框架名>|C:\\Users\\<用户名>"
git log -p --all | grep -iE "<项目名>|<模块包名>|<框架名>|C:\\Users\\<用户名>"   # 必须无输出
git ls-files | grep -E "(^|/)(latex|typst|epub|mdx)/|\.(pdf|epub)$"              # 必须无输出
```

第一条查工作区，第二条查全部历史（最易漏），第三条查被跟踪的产物；`.gitignore` 负责目录级兜底。若第二条命中：先 `git bundle create <仓库外路径>/<repo>-backup-YYYYMMDD.bundle --all`，再 `git filter-repo --replace-text <rules>` 做字面替换（保持提交信息与其他文件内容不变），校验 `git log -p --all` 0 命中且工作区树与清理前一致，确认远端无他人新提交后，才 `git push --force-with-lease`；备份不推远端。

## 10. 最小可行落地：只做三件事

如果暂时不改任何脚本与 `SKILL.md`，只做下面三件事，也能显著改善产物：

1. **阶段 2 先交 `01-module-tree.md` + `03-global-map.md` 的 spine**，再交 `outline.md`。

度量与证据层已经脚本化，接入成本很低，建议与上面三件事同时打开：

### A.4 结论

- 真正约束写作的：A0 判定、A2 spine、A4 三段式、每章 ≥2 图、`body3` 5 万下限、L1–L3 标级。
- 只做事后校验、不做写作约束的：双线比例回填、字数统计报告。它们仍有价值（防口径漂移、防比例失衡），但不应被描述成「写前必须满足的配额」。
- 证据不足且本轮无人使用的：每章图数上限、字数区间细分。列为形式主义候选，保留待确认，不删除。
